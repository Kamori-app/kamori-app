- `refresh_commit_and_password_reset_serialize_in_both_orders`: real `/auth/refresh` handler/service/rotation transaction versus production `update_user_password_file_and_revoke_refresh_sessions`. Reset-first holds the reset transaction after password/generation/session updates, sees refresh wait on its account lock, then commits and requires 401. Refresh-first holds just the existing session row; actual rotation holds its account lock and waits for that session row. A production reset transaction then demonstrably waits on the exact rotation backend. Releasing the session blocker lets rotation commit before reset. Requires the replacement/access token to be unusable, correct original-row replacement/request-id linkage, zero live sessions, generation exactly 1, and reset-invalidated exact retry. A fresh-password/current-generation rotation and exact retry return the same replacement token/id and leave exactly one live session.
- `passkey_registration_commit_rejects_reset_generation`: real OPAQUE reauth → add/start → valid WebAuthn attestation → add/finish persistence. Same two orders, pausing the actual finish transaction at its account lock (reset-first) or session lock (finish-first), before persistence. Reset-first requires 401 and zero passkey rows; both orders consume pending enrollment/registration state and reject old completion under old and fresh sessions. Finish-first requires successful real registration and preserves exactly one committed passkey per existing password-reset policy, while old sessions are revoked. Fresh current-generation registration succeeds after reset-first; reauth proof reuse and registration completion reuse are rejected because these are one-use flows, unlike refresh exact retry.
- Both passkey orders then perform a genuinely signed discoverable login, obtain a live session at generation 1, and successfully enroll a new device with the resulting bound capability. This proves retained-passkey new authentication eligibility rather than inventing deletion semantics.
- Both tests snapshot unrelated users, all their refresh sessions and passkeys before the races and assert exact equality afterward. Old access authorization uses production durable session checks. The refresh test additionally checks the unrelated live access capability remains eligible.

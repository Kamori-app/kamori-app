## Findings

### S01 — P1: A lost invite redemption response cannot be retried

Location: `apps/cloud-server/src/features/invites/repositories.rs:191`, `:282`; service maps the result to HTTP 400 in `features/invites/services.rs:155`.

The lookup requires `used_count < max_uses` before considering who previously redeemed the invite. The first transaction atomically activates membership and increments used_count to 1 (all issued invites have max_uses=1); an identical request by the same user subsequently returns InvalidOrExpired. The HPKE/shared-key ciphertext is returned only by this response. Losing that response can leave a recipient an active member but without the key package needed to install device/recovery packages or read data. SPEC section 4 promises exactly idempotent network retries.

Reproduction: create a valid current-epoch invite, call `redeem_invite_code_tx(pool, hash, recipient)` twice. First returns Redeemed; second returns InvalidOrExpired. The existing integration test stops after the first redemption. Browser `tests/acceptance/specs/sharing.spec.ts:87` currently explicitly expects a second same-recipient request to fail, encoding the contract mismatch.

Minimal fix: return the committed redemption outcome for the same recipient and exact redemption request without consuming another use, while still rejecting other recipients and revoked memberships/stale epochs. A stable request id plus durable response fields is preferable if manually submitting the code again must differ from retrying. Test first success/lost response/exact retry, different recipient, concurrent redemption, expiry/revocation/rotation after redemption. Update the acceptance assertion to the chosen explicit retry contract.

Evidence status: deterministic source-path proof; runtime reproduction is pending the controller's isolated PostgreSQL setup.

### S02 — P1: Purging a security space permanently leaves its operation bytes charged

Location: `apps/cloud-server/migrations/202608230010_signup_oplog_limits_and_indexes.sql:58`–`:61`; `features/operations/repositories.rs:141`; deletion path `platform/maintenance.rs:163`.

The operation_log AFTER DELETE trigger obtains the account owner by SELECTing the parent security_spaces row. When deleting a security space, its ON DELETE CASCADE removes operation rows after the parent has ceased to be visible. The trigger finds no owner, so UPDATE users WHERE id=owner_id updates no account. No security-space delete trigger compensates. Deletion removes actual operations but account.operation_bytes remains positive. Trash purge repeats this drift, eventually causing otherwise empty accounts to hit operation storage quota. Account deletion also invokes this path; that account is anonymized, but the normal 30-day space purge affects active accounts.

Reproduction: create owner/workspace/device/space, insert one operation, record users.operation_bytes, DELETE security_spaces WHERE id=..., read users.operation_bytes. Expected 0, source produces original charge. A direct DELETE operation_log while its parent exists does decrement correctly.

Minimal fix: a new migration should subtract OLD.operation_bytes from its owner in a BEFORE DELETE security_spaces trigger; keep child-row accounting correct for direct operation deletes, avoid double subtraction, and repair pre-existing drift by recomputing user operation totals. Regression should cover direct row deletion, direct space deletion, workspace cascade, and trash-maintenance purge, with blob counters checked alongside operation counters.

Evidence status: PostgreSQL cascade/trigger source analysis; awaiting runtime confirmation.

### S03 — P1: Distinct concurrent appends on one space can deadlock on a row-lock upgrade

Location: `apps/cloud-server/src/features/operations/repositories.rs:106` and `:146`.

Each append first takes FOR SHARE on its security space to recheck authorization. A new operation then tries to upgrade that row to FOR UPDATE for quota/sequence allocation. Two requests with distinct client_op_ids take different advisory locks, can both obtain SHARE, and then block each other's UPDATE conversion. PostgreSQL deadlock detection aborts one; the service exposes an internal server error. This affects ordinary concurrent offline sync from two clients. Same-id retries are serialized by their advisory lock and do not expose this defect.

Reproduction: two transactions each acquire SHARE on the same space, then concurrently execute the quota FOR UPDATE query; one errors with SQLSTATE 40P01. For an application-level test, hold scheduling at the first share-lock boundary and append two distinct signed operations concurrently.

Minimal fix: acquire the strongest required space lock on the initial authorization query (e.g. FOR UPDATE OF s, FOR SHARE OF sm,d), maintaining consistent space-before-account ordering. Add a deterministic distinct-id concurrency regression checking both successes, unique monotonic sequences, and correct counters. Existing `append_is_signed_authorized_and_idempotent` only tests concurrent calls for the SAME client_op_id.

Evidence status: deterministic conflicting-lock schedule from source; awaiting runtime confirmation.

### S04 — P1: Approved device authorization can create a new session after account recovery

Location: `apps/cloud-server/src/features/auth/services/device_authorization.rs:37`, `:223`, `:274`; `auth/repositories/refresh_tokens.rs:153`; recovery invalidation `auth/repositories/account_recovery_attempts.rs:147`.

An approved external-browser flow records user_id/username/key package in ephemeral state, but no approving session/device or account credential generation. The first token exchange creates a new refresh session if the user is merely active. Recovery revokes existing sessions/devices/passkeys but does not invalidate these approved flows. A native client holding an already-approved device_secret can wait until after recovery and mint a fresh session and enrollment grant during the ten-minute flow lifetime, receiving the previously approved AMK package as well. Password change has the same revocation gap.

Reproduction: start flow and approve it; recover the account or change its password before making the first token poll; poll with original flow_id/device_secret. Source accepts and creates an active refresh session after the reset.

Minimal fix: bind approval to durable account credential generation and approving authorization, then validate that binding atomically when creating the durable refresh session. A revoked/reset generation must never create a first session; legitimate exact retries of an already-created still-active session must remain idempotent. Add reset-before-first-poll and password-change-before-first-poll tests plus valid exact retry and revoked replacement tests.

Evidence status: complete cross-service source trace; not yet exercised against HTTP/PostgreSQL.

### S05 — P1: An OPAQUE exchange started before password reset can authenticate the old password afterward

Location: `apps/cloud-server/src/features/auth/services/signin.rs:68`, `:109`; `platform/security/opaque.rs:156`–`:169`, `:184`–`:200`.

login_start captures serialized ServerLogin state derived from the old password record under username/flow_id. signin_finish fetches the current UserRow but verifies the old serialized exchange without comparing the password-record fingerprint or an account authentication generation. Resetting/changing the password between these calls does not invalidate the pending proof. Finishing the saved old-password exchange creates a new refresh session after the reset; recovery also removed TOTP, so this path now observes TOTP disabled.

Reproduction: complete client-side old-password OPAQUE finalization but retain it; recover account using kit to a new password; submit retained signin_finish with old flow_id. The old state still verifies and complete_login creates an unbound active session plus a valid enrollment grant. The returned encrypted master key is current (wrapped for the new password), so it should not be claimed that this alone decrypts the new password wrapper; unauthorized authentication/session resurrection is the demonstrated impact.

Minimal fix: bind an exchange to the exact password-record fingerprint or durable auth generation and check that value transactionally when issuing a refresh session. Apply the same rule to TOTP continuations and other deferred authentication grants. Preserve independent flow handles. Add old-signin-across-recovery and old-signin-across-password-change regressions, ensuring failed stale proofs create no sessions and valid fresh signin remains functional.

Evidence status: complete cross-service source trace; pending runtime verification.

## Positive implementation observations

- Feature/service/repository split keeps HTTP transport out of durable transactional logic; SQL binds values rather than interpolating identifiers from untrusted inputs.
- Invite issuance and redemption serialize on the space row against rotation; ownership/role and key epoch are checked server-side.
- Operation signature verification is repeated authoritatively under locks where rotation snapshots need it, and duplicate append retries are still authorization-sensitive.
- Recovery state is durably tracked in PostgreSQL and exact completed retries are request-hash bound, avoiding lost-response lockout.
- Blob random IDs are per-space, private object keys never reused, quotas reserve before external storage, and egress reserves across app nodes. Disconnects conservatively charge observed upstream bytes; crash cleanup charges full unknown reservations.
- User/admin TOTP secrets are encrypted with separate domains, user/device key packages remain opaque, and metrics do not expose dynamic identifiers.
- Admin passkey removals lock the identity row to protect its last-key invariant, and passkey name uniqueness is enforced in the database.

## Confirmed findings

### U01 — Web task editing silently changes due timezone and instant (P1)

**Location:** `apps/web-frontend/src/lib/components/app/TaskWorkspace.svelte:84`, `:104`–`:106`; helper `apps/web-frontend/src/lib/pim.ts:765`.

Opening a zoned task fills the input with the original zone's wall clock. Saving always calls `localDateTimeToTemporal(dueAt)` without the original zone or an unchanged-value check. In a UTC browser, a task due 18:30 Asia/Tbilisi (14:30Z) becomes 18:30 UTC after editing only its title. Date-only due values similarly become timed zoned values; seconds are truncated by the input formatter. This violates SPEC §7's partial-edit preservation and shifts synced deadlines.

**Focused executed reproduction:** `TZ=UTC bun -e` importing `pim.ts`, passing `localDateTimeToTemporal('2026-08-28T18:30','Asia/Tbilisi')` through `temporalToInputValue` and then the editor's `localDateTimeToTemporal(input)`. Before UTC=`20260828T143000Z`, timezone=`Asia/Tbilisi`; after UTC=`20260828T183000Z`, timezone=`UTC`.

**Minimal fix:** Preserve the original due record when its displayed input is unchanged (including date-only type and seconds); on a deliberate change retain the existing zone, or expose an explicit zone choice. Follow CalendarWorkspace's original-value preservation approach.

**Regression:** Render/edit/save a task title with a foreign-zone due, date-only due, and nonzero seconds; assert the persisted due field stays byte-for-byte equivalent. Then explicitly edit the due time and assert the intended instant/zone.

### U02 — Web recurrence applies the event timezone twice (P2)

**Location:** `apps/web-frontend/src/lib/pim.ts:844`–`:860` (especially `:859`–`:860`).

`temporalToDate` resolves zoned DTSTART to a real UTC instant, which is passed to RRule as `dtstart` together with `tzid`. RRule interprets DTSTART's UTC components as the floating wall clock for TZID, applying the offset again. Repeated events appear on the wrong calendar day near midnight and can use the wrong recurrence anchor across DST.

**Focused executed reproduction:** Under `TZ=UTC`, use start=`localDateTimeToTemporal('2026-08-28T07:00','Asia/Tbilisi')`, end 07:30, `FREQ=WEEKLY`. The canonical instant is Friday 03:00Z; `recurringIntervalOccursOnDay` returns **true for Thursday 2026-09-03, false for Friday 2026-09-04**. Expected false/true.

**Minimal fix:** For TZID rules, construct RRule's floating DTSTART from `PimTemporal.local`, retaining the real UTC instant for interval comparison; handle UNTIL and durations consistently. Avoid removing TZID because that would break DST.

**Regression:** Foreign-zone timed recurrence on a UTC browser, both signs of offsets crossing midnight, and DST-crossing weekly recurrence. Existing tests cover only all-day weekly rules.

### U03 — Mobile UTC recurrence applies the device offset twice (P2)

**Location:** `apps/dav-bridge-mobile/lib/src/models/bridge_models.dart:510`–`:518`, `:536`.

`_floatingTemporal` uses `toEditorDateTime()`, which converts `kind == 'utc'` to device-local fields, then labels those fields UTC. `_recurrenceInstant` treats the generated value as a real UTC instant and calls `toLocal` again. Native-created events use UTC records, so ordinary mobile recurring events are affected in non-UTC zones.

**Executed reproduction:** `/private/tmp/kamori-audit-20261015/client-repro.dart` imported the real model via the existing package config, using a weekly event starting `20260828T180000Z` and ending 18:30Z. Under `TZ=Asia/Tbilisi`, original start prints Friday 22:00 local, yet `pimIntervalOccursOnDate` reports **2026-09-04 false; 2026-09-05 true**. Expected true/false.

**Minimal fix:** Build UTC recurrence anchors from `toDateTime()`'s UTC fields; use original local fields only for zoned records and calendar date fields for date-only values. Preserve zoned DST semantics separately.

**Regression:** Run the same UTC recurrence under UTC and two non-UTC TZ values, plus zoned DST and all-day cases. Existing model tests run simple all-day recurrence and separately test a single zoned instant.

### U04 — Another tab's CSRF rotation unnecessarily signs the current tab out (P2)

**Location:** `apps/web-frontend/src/lib/api/cloud.ts:25`–`:27`, `:546`–`:570`; `apps/web-frontend/src/lib/auth/session-flow.js:49`–`:52`; `apps/web-frontend/src/lib/components/app/AppWorkspace.svelte:282`–`:290`.

The CSRF value is indefinitely cached per JS tab while the host-only CSRF cookie is shared and rotated on refresh. Deterministic sequence: sign in/open two tabs so both cache A; tab 1 refreshes, advancing shared cookies to B; tab 2's access token expires and it sends cached A alongside cookie B. Server `apps/cloud-server/src/features/auth/transport/csrf.rs:25` returns HTTP 401 `csrf token mismatch`. Although refresh clears its local cache in `catch`, `runWithAccessRefreshRetry` immediately handles the 401 as session expiration, clears the access token, and gives no bootstrap retry. A healthy refresh session is rejected locally. Web Locks around sync do not update the second tab's cached CSRF token, so serialization alone does not solve this.

**Evidence:** Complete client/server call path inspected; no live multi-tab server reproduction executed. The mismatch and sign-out follow directly from the above branches.

**Minimal fix:** Bootstrap current CSRF after acquiring a cross-tab refresh lock, or identify a CSRF mismatch and re-bootstrap/retry safely before classifying it as refresh-session expiration. Preserve generation-specific durable rotation request IDs. Coordinate concurrent in-tab refreshes too.

**Regression:** Two tabs sharing cookies, one rotates before the other refreshes; assert the latter stays signed in. Include lost-body/header-advanced retry, concurrent Settings/AppWorkspace requests, and genuine revoked-session 401.

### U05 — iOS periodic sync lacks the native background capability configuration (P2)

**Location:** `apps/dav-bridge-mobile/ios/Runner/Info.plist:1`; `apps/dav-bridge-mobile/ios/Runner/AppDelegate.swift:6`; scheduling at `apps/dav-bridge-mobile/lib/src/services/background_sync_service.dart:101`.

The app schedules `kamori_background_sync_task` as a Workmanager periodic task, but Info.plist contains neither `UIBackgroundModes` (`fetch`) nor `BGTaskSchedulerPermittedIdentifiers`. The installed pinned `workmanager_apple-0.9.10` implementation schedules a `BGAppRefreshTaskRequest` with that identifier (`WorkmanagerPlugin.swift:720`), catches a failed submission and only logs it (`:739`); Dart can therefore show background sync enabled even though the task cannot be admitted by iOS. Native background plugin registration is also absent from AppDelegate and needs validation when wiring this up.

**Evidence:** App configuration and the already-installed plugin's actual scheduling implementation inspected. No physical iOS scheduler execution performed.

**Minimal fix:** Add required iOS permitted identifier/background mode and configure native background plugin registration as required by the pinned plugin. Verify task delivery on a physical release device and surface scheduling failure instead of relying on a successful Dart Future alone.

**Regression:** Configuration assertion matching the Dart task identifier and native plist; integration/device check executing the callback after suspension and restart.

### U06 — Background sync never reconciles enabled system projections (P2)

**Location:** `apps/dav-bridge-mobile/lib/src/services/background_sync_service.dart:60`–`:82`.

The background callback reconstructs and syncs the encrypted cache, then returns without listing PIM items, configuring `NativeSystemProjectionService`, or projecting enabled collections. Foreground sync explicitly calls `_projectSystemCopies` (`bridge_controller.dart:290`) while the background path never does. With Calendar/Contacts integration and periodic sync enabled, another device's changes can be in the local encrypted cache for hours while the user's system Calendar/Contacts copies remain stale until opening Kamori. A deleted event/contact remains visible in the system store despite successful background sync.

**Evidence:** Source-traced entire callback; no provider/device runtime execution. This follows the intended next-sync reconciliation behavior in SPEC §9 and the user-facing one-way projection contract.

**Minimal fix:** After successful sync, load materialized items, configure projection with the snapshot/vault account, read persisted opt-ins, and reconcile enabled projections; do not request new permission in a background job. Handle projection failures independently from encrypted-sync success.

**Regression:** Extract an injectable background runner; fake bridge/provider test should verify opted-in create/update/delete reconciliation, no projection when disabled, and no permission prompt. Add a real OS provider background test.

### U07 — Failed queued logout revocation blocks access to a different persisted offline session (P2)

**Location:** `apps/dav-bridge-mobile/lib/src/state/bridge_controller.dart:83`, `:265`–`:271`.

Restore awaits network-dependent `_retryPendingRevocation()` before even reading the saved runtime. A queued revocation can coexist with a later successful login: sign out A while offline to queue it, sign in B when A's server is still unavailable (or a transient A revocation failure occurs), then restart offline. Pending A revocation throws and the outer restore catch marks B unauthenticated without loading its encrypted offline cache. The queue can also originate from incomplete-login rollback. SPEC §6's offline availability should not depend on a different session's revocation endpoint.

**Evidence:** Deterministic source path and persisted-store lifetimes inspected; no Flutter integration reproduction executed.

**Minimal fix:** Retry pending revocations best-effort independently of restoring the current snapshot; retain the queue and show an appropriate warning. Keep local account matching checks strict.

**Regression:** Valid current snapshot/vault plus a queued revocation whose network request throws; assert current offline PIM loads and queued revocation remains for retry.

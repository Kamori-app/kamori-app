# Исправление границ доверия E2EE

Дата: 2026-10-16. Статус: проект для проверки пользователем; продуктовая реализация ещё не начата.
Ветка: `fix/e2ee-trust-boundaries`, исходный commit `c8fddb9`. Ревизия 2 после независимой валидации и верификации проекта; проверенный предшественник — `7d2f0d5`.

## Цель и критерии результата

Исправить подтверждённые пути выдачи ключей подставленным получателям, зависание офлайн-очередей после смены доступа, отсутствие независимых доказательств истории и отсутствие процедуры замены скомпрометированного master key. Сохранить офлайн PIM, MessagePack и общий Rust core для web/WASM и native/FRB.

Проверяемый результат — отрицательные интеграционные тесты с изменяющим ответы сервером и положительные сценарии регистрации, подключения устройства, приглашения, отзыва доступа, восстановления и повторной отправки после потери ответа. Зелёные тесты отдельных криптографических примитивов не заменяют эти сценарии.

## Сохраняемые продуктовые ограничения

Регистрация остаётся только в web; desktop и mobile поддерживают вход в существующий аккаунт. Sharing использует генерируемые клиентом одноразовые коды, без ввода member UUID в UI. Срок приглашения выбирает пользователь: от 15 минут до 7 дней. Подписанный grant фиксирует срок, роль, service/space и capability; клиент проверяет срок по локальному времени, а честный сервер дополнительно обеспечивает TTL и exact-retry семантику. Клиентские часы не являются независимым доказательством глобальной свежести. Mobile поддерживает только Android/iOS, без localhost DAV. System projection остаётся opt-in отдельно для каждой коллекции.

## Зафиксированные причины

1. `AppWorkspace.svelte` при ротации доверяет HPKE-ключам `/members` и `/devices`; аналогичный путь есть в mobile Rust. В `SettingsModal.svelte::approveDevice` уже существующие ключи упаковываются для серверного ключа устройства.
2. Desktop открывает `verification_uri` из ответа API; браузер берёт HPKE-ключ из inspect-ответа и упаковывает для него master key. Пользовательский код не подтверждает ключ получателя.
3. Запись операции проверяет текущую эпоху и авторизацию перед поиском точного повтора. После lost ACK и ротации ранее принятая операция не согласуется через обычный append. Офлайн-очереди отправляют прежние envelopes и останавливаются на первой ошибке.
4. Подпись envelope не включает серверные `space_seq`/`next_cursor`. Клиенты могут сохранить курсор за скрытой операцией. Подписанный snapshot не доказывает полноту истории или свежесть.
5. Пароль и Data Recovery Kit переупаковывают тот же master key; device revoke не меняет эпохи пространств. Утечка master key сохраняет recovery-идентичность и возможность снова запустить kit recovery.

## Модель угроз и ограничения

Сервер API, БД, хранилище объектов и TLS-терминатор могут менять, скрывать, повторять и разделять ответы между честными клиентами. Секреты честных клиентов считаются неизвестными атакующему, кроме явно рассматриваемого случая старого master key. OPAQUE не исключает offline guessing при полной компрометации серверных записей/секретов; стойкость пароля и согласованные KSF-параметры остаются предпосылкой. Криптографические примитивы и установленный код клиента считаются исправными. Web origin и разблокированное устройство — отдельная граница: выполняющийся там вредоносный код получает данные, к которым имеет доступ клиент.

Первичную принадлежность чужого публичного ключа нельзя доказать ответом того же сервера. Подпись незнакомым ключом не доказывает владельца. Числовой курсор, подпись сервера и самоподписанный каталог не устраняют эту проблему.

Клиент без связи с независимым доверенным источником не способен доказать, что сервер не скрыл самый новый хвост журнала. Цель первого протокола — проверяемое продолжение закреплённой истории, обнаружение пропусков/подмен/отката и обнаружение разделённых историй при обмене контрольными точками. Без такого обмена интерфейс сообщает границу проверенной истории; он не обещает глобальную свежесть.

Стирание уже раскрытого plaintext, защита работающего вредоносного web origin и восстановление секретности старой истории после кражи долговременного ключа не объявляются исправляемыми свойствами.

## Рассмотренные подходы

- Локальные запреты и проверка последовательности: быстро закрывают отдельные пути и улучшают очередь, но не аутентифицируют чужие устройства и не доказывают полноту журнала. Это этап сдерживания, не конечная защита.
- Подписанные идентичности и состав участников, независимое установление первого доверия, клиентская цепочка журнала и отдельная смена корневых секретов: рекомендуемый путь. Он сохраняет существующие криптографические библиотеки и PIM-модель; требует новой версии протокола и явной миграции.
- Замена группового протокола на MLS: требует отдельного проектирования identity, recovery, offline history и доставки. Сам по себе MLS не решает доверие к первой идентичности или свежесть скрытой сервером истории. В данный цикл не входит.

## A. Идентичности и выдача ключей

Добавить общие versioned canonical-encoding структуры и проверку в Rust core. Использовать существующие Ed25519, X25519, HKDF-SHA256 и HPKE; не добавлять собственных криптографических примитивов.

Account identity связывает service scope, fingerprint корневого ключа, identity generation, публичный ключ подписи аккаунта и recovery HPKE key. При signup server UUID ещё неизвестен: исходный profile подписывается без него, после регистрации публикуется отдельная подписанная routing-привязка к UUID. UUID и username сами по себе не являются корнем доверия. Device certificate, подписанный ключом аккаунта, связывает origin/account/generation, device UUID, обе публичные пары устройства и версию формата. Контексты подписей и вывода ключей различаются по назначению; поля имеют однозначное представление и ограничения размера.

Для своего аккаунта клиент сверяет публичную идентичность с локально полученной из master key. Для чужого аккаунта корень должен быть закреплён через доверенный канал подключения, а не только получен из server directory. При первом контакте допустим проверяемый код/QR; смена закреплённой идентичности требует повторной проверки. TOFU не обозначается как подтверждённая личность.

Для обычного подключения собственного нового устройства initial owner policy явно делегирует действующему member root право сертифицировать/отзывать только свои device keys без изменения роли/чужих участников. Root-authorized device-admission control включается в журнал по правилу предыдущего состояния; owner не обязан быть онлайн, если такая делегация уже закреплена. Подпись нового device/root сама по себе не меняет membership. Новый клиент получает проверенные peer pins/checkpoints из trusted pairing либо account-signed/encrypted export под своим master key. Серверная резервная копия такого export доказывает подлинность сохранённой границы, не её последнюю версию. При отсутствии любого подлинного anchor/pin неизвестные foreign identities не используются для выдачи ключей/новых writes; enrollment собственного устройства может завершиться, а затронутые пространства остаются явно unverified/blocked до trusted bootstrap.

**VV-R1 — доверие после компрометации.** Разрешение account trust export выше относится к обычному подключению при отсутствии известной компрометации корня. При compromise recovery export/checkpoint/manifest, аутентифицированный только скомпрометированным прежним master/root, не устанавливает peer pins, recipient authority или подлинность истории. Для свежей выдачи ключей требуются независимо сохранённые доверенные anchors и подтверждённые получатели либо повторная независимая сверка; изменения прежнего owner/root также не принимаются автоматически. История с одним таким доказательством сохраняется как unverified/salvage. При отсутствии независимых оснований space remediation остаётся pending/repair без рассылки новых ключей неизвестным получателям и без заявления подтверждённой непрерывности истории.

Owner-signed membership manifest фиксирует поколение пространства, эпоху, предыдущий manifest hash, корни участников, роли и разрешённые сертификаты устройств. Полный список получателей новой эпохи вычисляется из проверенного manifest; серверный список используется для транспортной доставки, а не как authority добавления нового получателя. Пакеты recovery также проверяются против manifest. Переходы membership, account/device authorization, эпох и snapshots упорядочены в том же аутентифицированном журнале: переход в позиции N разрешается состоянием непосредственно до N и активирует новое состояние для N+1. Обычная запись ссылается на head, вычисленный клиентом у её предшественника; сервер не может независимо выбрать старый подлинный manifest. Ротация атомарно связывает предыдущий log head, old/new membership heads, commitments получателей/пакетов и snapshot manifest. Сохраняются исторические сертификаты и границы их допуска/отзыва.

**VV-T1 — смена владельца.** Security-space ownership меняется только отдельным аутентифицированным control transition: предыдущий проверенный owner подписывает offer с space/log generation, predecessor head, новой owner identity, правами и условиями; новый owner подписывает acceptance тех же bytes. Successor root должен уже быть независимо проверенным member root либо пройти явную сверку. Переход активируется по правилу N→N+1, сохраняет checkpoints и key/history entitlements; повтор, конкурентный offer и устаревший head разрешаются exact-retry/CAS без бесшумной подмены. Server-only изменение owner_user_id не меняет authority клиента. После активации прежний owner не подписывает owner-only controls, если не получил отдельную допустимую роль. Передача workspace ownership отдельно меняет административные/квотные права и сама по себе не передаёт криптографическое владение пространствами.

Версия пакета ключа привязывает пространство, эпоху, получателя, identity generation и manifest hash в аутентифицированном контексте. Перенос пакета в другое пространство/эпоху/получателю отвергается.

Приглашение продолжает использовать генерируемый клиентом секретный одноразовый код; сервер получает только hash и ciphertext. Формат приглашения должен переносить owner identity, manifest и контрольную точку истории под защитой секрета. Допуск нового участника в будущие ротации требует аутентификации его account identity: простого утверждения сервера «код погасил этот UUID» недостаточно. Владелец подписывает grant с invitation verification key, отдельно выведенным из секрета; вступающий подписывает claim и этим ключом, и своим account root. Сервер, знающий лишь lookup hash, не может подставить root в claim. Owner-клиент проверяет claim при следующей синхронизации и подписывает однократный переход membership. До него нет автоматической рассылки последующих ключей новому root и подтверждённого права editor; приглашённый может читать переданный текущий snapshot. Для v2 секрет кода имеет не менее 128 бит энтропии; прежние коды не переобозначаются как v2.

Все пути выдачи ключей используют один проверяющий API: создание/ротация пространства, approveDevice, invite redeem/admit, подключение своего устройства, recovery repair. Не допускается обход через legacy fallback.

## B. Подключение desktop через браузер

Desktop сам формирует доверенную web-ссылку и привязывает её к локально созданному ephemeral HPKE key, flow UUID и версии bootstrap. Полученный от API URI проверяется против отдельно настроенного доверенного web origin; произвольный origin/path не открывается, адрес собирается локально. Production требует HTTPS, тестовое HTTP разрешается только для явного loopback fixture.

Браузер использует commitment ключа, полученный непосредственно из открытой native-клиентом ссылки; ключ из inspect-ответа обязан ему соответствовать. Отсутствие или несовпадение commitment останавливает операцию до encrypt/upload master key. Одного server-assigned user code недостаточно. Пользователь явно подтверждает аккаунт и подключение; автоматического approve при открытии URL нет.

**VV-S1 — обратная аутентификация.** Native дополнительно создаёт независимый случайный 32-byte pairing secret и client nonce. Секрет передаётся только через fragment локально сформированной trusted-origin ссылки/QR; он не попадает в API start/inspect/approve/token, query string, серверные логи или telemetry. Браузер захватывает fragment до перехода к входу и удаляет его из URL/history; закрытие/потеря pending state требует нового pairing. Native и browser требуют HPKE PSK mode по RFC 9180 §5.1.2, непустой transcript-bound psk_id и ровно 32-byte секрет с полной CSPRNG-энтропией. Пустой/короткий PSK и fallback в Base запрещены приложением независимо от permissive API библиотеки.

Аутентифицированный transcript связывает версию, API/service и portal scope, flow, client nonce, recipient key, browser-approved account root/routing identity/generations и digest полного checkpoint export. Публичный info/AAD содержит известный pending контекст; approved account identity/generations и checkpoint export находятся в аутентифицированном payload. Дублируемые outer/header поля считаются недоверенными до проверки и затем обязаны точно совпасть с payload. Native принимает master/profile/checkpoints только после PSK authentication всего return payload и сверки с локальным pending transcript и уже имеющимися pins. Self-consistency полученного master с вложенным profile не является отдельным доказательством отправителя. Outer server/session identity проверяется только на согласованность, не определяет доверенный root и не переопределяет browser-approved identity. Без прежнего pin источником первого доверия является аутентифицированный browser payload, а не server metadata.

Срок pairing ограничивается локально; серверный ответ не может его продлить. Cancel/expiry/успех закрывают one-use pending flow, освобождают secret и ephemeral private key насколько позволяет runtime. Повторные poll/потеря ACK работают только с тем же pending transcript; ответ другого flow не активирует аккаунт.

Commitment публичного ключа не секрет, pairing secret — секрет. Оба должны прибыть через доверенный канал запуска приложения/QR; API не является этим каналом. Старый неподтверждённый bootstrap не получает master key; пользователь обновляет desktop. Self-hosted web origin задаётся явно пользователем/конфигурацией клиента.

## C. Офлайн-операции и смена доступа

Сохранять исходный подписанный envelope и порядок зависимостей до достоверного подтверждения. Ввести устойчивые состояния очереди: pending, awaiting-current-keys, awaiting-ack-reconciliation, blocked-access, blocked-author и blocked-causal-history. Ошибка одной записи/пространства не блокирует независимые пространства; зависимости внутри одной ветви не перескакиваются.

После изменения эпохи сначала получить и проверить актуальный key-control state и доступ. Затем согласовать неизвестный результат прежней отправки по operation UUID и digest исходного envelope. Новый read-only receipt lookup авторизуется текущим доступом аккаунта к пространству и не возвращает чужой plaintext. Этот lookup не разрешает запись отозванным устройством. Для authenticated-log версии подтверждение проверяется по включению точного envelope в подтверждённую цепочку.

Если запись уже принята, завершить исходную очередь без нового логического изменения. Отсутствие определяется только до конкретной проверенной вершины H: через сохранённый аутентифицированный inventory UUID/digest или привязанное к H non-inclusion proof. Один server receipt absent этого не доказывает. Согласовываются все сохранённые попытки envelope для этого логического UUID, включая предыдущие reseal, а не только исходный digest. При подтверждённом отсутствии и проверенном переходе к более поздней эпохе, который запрещает старую попытку на этой цепочке, действующий прежний author может переупаковать ту же семантическую операцию с тем же UUID и зависимостями. Replacement привязывается CAS к H; при изменении head сначала проверяется продолжение и повторяется reconciliation. Новый nonce и точные replacement bytes сохраняются до сети; повтор использует именно их. Неизвестные или иные bytes того же UUID — конфликт. Без полного доказательства запись остаётся awaiting-ack-reconciliation. Гарантия относится к проверенной ветви, не к ещё не обнаруженным forks.

**VV-L1 — причинное состояние.** Доказательство наличия UUID/digest не заменяет состояние semantic parent. Автоматический reseal разрешён только если проверяемый retained causal archive содержит нужные DAG edges и базовые состояния либо checkpoint сохраняет эквивалентное проверяемое causal evidence. Начальный rollout не включает общее удаление старых payload; будущая compaction обязана явно определить поддерживаемую границу offline history. Если для C(parent=P) после P→Q доступен только snapshot Q, C остаётся blocked-causal-history с исходными bytes и ключами для локального просмотра. Нельзя применить C к Q, сменить parent, показать C синхронизированной или удалить её из очереди. Пользователь может получить repair archive либо выполнить явно проверяемый импорт как новую операцию; зависимые записи тоже удерживаются, независимые продолжаются.

Исключённый участник и отозванный author не переподписывают изменения автоматически под новой личностью. Их черновики остаются локально зашифрованными, явно показываются как неотправленные и могут быть перенесены пользователем только туда, где у текущего устройства есть право записи. Удаление/экспорт черновиков — явное действие. Reader также не получает автоматическую повторную отправку.

Transient transport error сохраняет очередь и retry identity. Успешная синхронизация, pending и заблокированные черновики показываются раздельно; общий «всё синхронизировано» при постоянном отказе не отображается.

## D. Аутентифицированная история

Сначала запретить продвижение transport cursor за последнюю обработанную запись, пустые скачки, убывающий/повторный position с иными bytes и несовпадение страницы с её курсором. Не считать эту проверку криптографическим доказательством полноты.

В новой версии append клиент подписывает commitment к поколению журнала, позиции, hash предыдущей записи, UUID логической операции, digest точного encrypted envelope и hash проверенного membership state. Сервер атомарно выполняет compare-and-swap ожидаемой вершины и сохраняет запись. Повторная попытка сохраняет логическую operation identity; смена позиции при честной конкурентной записи не создаёт вторую PIM-операцию.

Клиент продвигает подтверждённую вершину только после проверки всей цепочки от локально закреплённой точки, сертификата автора и его роли в соответствующем membership state. Права текущего server directory не заменяют историческое доказательство допуска. Цепочка подписей/commitments и аутентифицированное соответствие logical UUID → принятый envelope digest/позиция сохраняются при сокращении payload history; позиции не перенумеровываются. Уникальность logical UUID проверяют и серверная транзакция, и клиенты при проверке цепочки; включение/отсутствие UUID остаётся доказуемым после purge payload. Legacy history/current-state floor обрабатывается отдельным явно server-trusted bootstrap, пока пространство не мигрировано; неожиданная дыра внутри установленного session не разрешает сброс pin. V2 purge требует подписанного checkpoint, разрешающего замену конкретного prefix.

Snapshot включает полный аутентифицированный manifest потоков и ветвей, покрываемую вершину и поколение журнала. Загрузка произвольного набора потоков не становится успешной полной загрузкой. Полное удаление пространства завершает поколение; его UUID нельзя переиспользовать для бесшумного обнуления pins.

В web pins и проверенное локальное состояние сохраняются одной IndexedDB-транзакцией под per-space lock/CAS. Native ведёт journal и отдельный high-water anchor в platform secure storage: crash на границе двух хранилищ требует восстановления подтверждённого продолжения, а не снижения secure-store pin. Это не защита от отката одновременно всех доверенных хранилищ. Несовместимое продолжение, откат ниже pin или другое содержимое на той же позиции переводят пространство в integrity-error без перезаписи уже подтверждённых данных. Новый клиент получает anchor при доверенном bootstrap/invite; без anchor он явно показывает неподтверждённую свежесть.

Подписанные контрольные точки можно сравнить через доверенное устройство/QR. Различные hashes одной позиции выявляют fork; расширение проверяется consistency proof. Изолированную сервером ветвь нельзя гарантированно обнаружить без независимого обмена/witness. Независимый witness не разворачивается автоматически этим изменением.

## E. Потеря устройства и компрометация master key

Разделить normal password change, normal kit recovery, device revocation и compromise recovery. Смена пароля по-прежнему меняет OPAQUE wrapper без непрошенной полной перешифровки данных. Интерфейс прямо сообщает, что это не замена украденного master key.

**VV-S2 — отзыв устройства.** Обычный revoke закрывает API sessions/certificate authority и будущую выдачу device packages при корректном сервере; он не отзывает уже скопированные ключи и recovery capability. Runtime-устройства владеют master key: при подозрении на компрометацию потерянного устройства пользовательский сценарий обязательно ведёт в полное root/space remediation, а не завершается после удаления certificate или одной смены эпохи. Только административный отзыв без подозрения на утечку остаётся отдельным действием с этим явным ограничением.

**VV-T5 — обычное восстановление kit v2.** Полный kit, подписанный one-use proof и новая OPAQUE registration восстанавливают прежний content root/identity и текущие допустимые пакеты, не объявляя лечение компрометации root. Reset увеличивает auth_generation; отзыв sessions/devices, удаление passkeys/TOTP backup codes и отключение TOTP явно показаны и подтверждены как состав recovery manifest, сохраняя текущую MVP-семантику. Исторические данные и черновики сохраняются; прежние author drafts переходят в blocked-author. Одни root words или runtime master без offline authorization seed не разрешают v2 recovery. По умолчанию root и offline authorization credential не меняются; их замена — отдельный compromise recovery/kit-regeneration. Прежний полный kit поэтому остаётся recovery authority, пока явно не заменён.

OPAQUE export_key — клиентский секрет для упаковки master; session_key известен также серверу и для этой цели не применяется. Упаковка v2 аутентифицирует service/account/root generation и сверяется с имеющимися pins. Успешный OPAQUE login не доказывает свежесть серверного key-control/history state.

Добавить отдельную подтверждаемую операцию смены master key/recovery identity с новым случайным master key и новым recovery kit v2. Kit v2 — версионированный переносимый файл с 24 словами content root, независимым случайным 32-byte recovery-authorization seed, account/service scope, generation и checksum. Если на момент создания kit имеются проверенные peer pins/log anchors/protocol floors, их export также сохраняется в этом независимо удерживаемом offline artifact с явной датой/границей наблюдения; это не обещает свежесть после экспорта. Отсутствующий anchor нельзя восстановить доказательством, подписанным только уже украденным root. Seed задаёт отдельный ключ подписи recovery proof и не хранится в runtime vault или в упаковке под master key; сервер хранит только публичный verifier. Одни 24 слова content root после миграции не являются полным средством восстановления. Kit должен быть сохранён и повторно импортирован/проверен до серверного commit. Повторная выдача полного kit из Security требует нового независимого seed и явно отзывает прежний authorization credential; его нельзя восстановить из одного runtime master key. Операция требует свежего action-scoped подтверждения текущего пароля и настроенного независимого фактора либо полного offline kit v2; possession старого master key само по себе не разрешает тихую смену проверенного корня. Recovery proof подписывает одноразовый challenge и точный manifest операции, чтобы записанный proof нельзя было применить к другому reset. Обычная authenticated смена корней не удаляет настроенные факторы; сброс потерянных факторов при kit-only восстановлении является явно подтверждаемой частью manifest.

До commit клиент получает и проверяет все известные ему retained/entitled текущие и исторические ключи, включая зависимости локальных drafts и кеша. Полнота проверяется по известному доверенному inventory и server inventory под CAS; неизвестное всем доверенным клиентам скрытое прошлое доказать полным нельзя. Каждый новый пакет и wrapper локально открывается и сравнивается с исходным ключом. Исторические ключи получают новые пакеты либо сохраняются в явном archive под новым root/device-local key. Missing/corrupt известный ключ блокирует подготовку и показывает потребность в repair, а не считается отказом от истории. Клиент строит новый пакетный набор и зашифрованную упаковку. **VV-L2 — передача полномочий восстановления.** До account commit прежний проверенный owner root публикует в журнал каждого своего пространства typed RecoveryIntent, разрешённый предыдущим membership state. Он связывает recovery operation UUID, точный recovery-manifest digest, predecessor head, новый root, replacement-device certificate и разрешённые finalize/abort controls; обычные writes замораживаются. Intent заранее делегирует только точному R_new/D_new завершение этого перехода. При lost-all-device kit-only recovery специальный узкий capability допускает root-authored intent без отсутствующей старой device signature/session; это не допуск обычных PIM writes от отозванного устройства.

Account commit проверяет полное покрытие текущего inventory/intents и root/recovery/auth CAS. Новый replacement bootstrap затем отправляет разрешённый finalize control с доказательством exact intent и новым root/device, не оживляя прежние devices. Finalize и precommit abort — явные исключения из ordinary-write freeze. Остальные участники независимо проверяют новый root прежде, чем принять новую identity и выдавать ей ключи: прежняя root signature сама по себе недостаточна. До account commit отмена дописывает root-authorized abort; после commit разрешено возобновление, не откат к старому root. Изменение inventory/manifest требует append-only intent revision либо abort/reprepare всех затронутых intents; root-generation/operation CAS не допускает commit конкурирующих переходов. Частичная подготовка и потеря ответа сохраняются как pending/repair с точным retry/status, а не успешное завершение.

В одной серверной транзакции меняются OPAQUE-bound wrapper, recovery verifier, identity generation и пакетный набор, увеличивается auth_generation, отзываются старые sessions/devices и незавершённые password/reauth/recovery/enrollment capabilities. Exact retry возвращает тот же результат; частичная подготовка не удаляет старую возможность восстановления.

**VV-L3 — разные поколения.** auth_generation меняется при password reset/change, обычном recovery и root replacement; identity_generation меняется при замене content/signing/recovery root; recovery_auth_generation — при замене offline authorization seed; inventory_generation — при изменении покрываемого состава/пакетов. Эти счётчики не подменяют друг друга; kit и proof связывают нужные поколения. Финальная мутация каждого известного аккаунту pending proof проверяет захваченный auth_generation в той же транзакции; чтение текущего поколения только на finish недостаточно.

Для discoverable passkey challenge, где аккаунт неизвестен на start, сохраняется монотонный committed issuance barrier. Каждая security mutation атомарно записывает новый barrier аккаунта; выдача challenge упорядочена с commit изменения barrier, а finish после определения аккаунта отвергает challenge до его последнего barrier. Это логический барьер, не сравнение wall-clock timestamps. Сохранение credential не сохраняет старые challenges: новая ceremony после commit допустима, старая — нет. Узкое exact-retry/status исключение относится лишь к уже committed exact operation, не выдаёт новую общую сессию.

Новый master key никогда не упаковывается под скомпрометированный прежний master key, включая временные resume-артефакты. Локальный rekey journal защищается независимым device-local ключом и/или новым kit, хранит точные request bytes и не загружается на сервер в раскрывающем новые секреты виде. Смена master key требует transactional migration локального vault: при crash до/после commit остаётся однозначно восстанавливаемое состояние, а старый kit после commit больше не авторизует новый recovery при корректном серверном verifier. Новый random root и новые ключи нельзя вычислить из старого kit; вредоносный сервер всё ещё способен игнорировать собственную API-авторизацию и воспроизводить старое состояние. Отдельный bound replacement-device bootstrap и узкий status/exact-retry capability сохраняются через commit, отзывающий прежние сессии. Device-local outbox старых авторов сохраняется как blocked-author, не переподписывается молча.

На корректном сервере каждая операция выдачи recovery package проверяет identity/recipient generation и fingerprint, чтобы конкурентная публикация старого пакета не пересекла commit. При вредоносном сервере клиент обязан отвергнуть identity ниже доверенного pin до шифрования/загрузки; server-side rejection после upload уже не защищает ciphertext. Ранее изолированный владелец, не узнавший новую identity, может продолжать выдавать секреты старой подлинной identity на скрытой старой ветви. Немедленный отзыв для такого клиента без независимого обмена не гарантируется. Соблюдается порядок блокировок space → account → device; несколько пространств блокируются в детерминированном порядке. Каждая вставка/удаление и in-place update membership/package/recipient identity/epoch/entitlement, включая upsert и появление нового пространства, меняет account inventory generation. Несколько account/device rows также блокируются в детерминированном порядке; account-first helper не вызывается перед необходимыми space locks. После блокировок inventory CAS и coverage проверяются снова; изменение inventory требует перезапуска подготовки, а не частичного commit. Известные атакующему space keys требуют также ротации соответствующих пространств. Собственные пространства помечаются remediation-pending и до завершения свежей эпохи не подтверждают новые cloud writes; локальные drafts остаются доступны. Пространства ротируются с новыми проверенными identities/manifest и текущими snapshots. Для чужих пространств требуется действие их владельца. Завершение отмечается только после независимой проверки им нового root, commit новой эпохи/recipient manifest и принятия этой точки участвующими клиентами; до этого раздел показывает owner action/remediation pending. Account commit сам по себе не завершает восстановление безопасности чужого пространства. Простая переупаковка того же space key не заявляется восстановлением его секретности.

Если прежний account root действительно скомпрометирован, его подпись под новым root недостаточна для других участников. Они повторно проверяют новую identity. Возврат секретности старому plaintext и уже скопированным ciphertext/wrappers невозможен.

## F. Web origin, хранение и внешние копии

Локальный browser unlock остаётся opt-in; при выходе/блокировке минимизируются активные ключи, но JavaScript zeroization не объявляется гарантированным стиранием всех копий памяти. Неэкспортируемый WebCrypto key не объявляется защитой от same-origin script.

Native использует существующие SQLCipher и platform secure storage без mock fallback в production. Не добавлять обязательный biometric prompt в фоновую задачу под видом незаметного исправления.

System projection остаётся opt-in per collection и явно обозначает выход plaintext за границу Kamori. Выключение с удалением owned copies не обещает удаление внешних backups/cloud copies. Локальный DAV остаётся authenticated loopback-only.

## Миграция и совместимость

Взаимосвязанные изменения выкатываются этапами на уровне протокола, а не скрытым изменением совместимости существующих аккаунтов. Production-миграция и публикация не выполняются в рамках локальной разработки без отдельного разрешения.

Новая версия протокола обязательна для усиленных путей выдачи ключей и authenticated-log spaces. Несовместимые клиенты получают явный upgrade-required; сервер не делает silent downgrade. Новые поля остаются bytes-oriented MessagePack; u64 positions передаются без потерь точности JavaScript и проверяются на границы SQL integer. Не подписывать произвольный порядок полей MessagePack map. Все подписанные структуры используют фиксированный versioned canonical transcript. Regenerations WASM/FRB коммитятся вместе с surface changes.

Существующий master key позволяет подтвердить свой account root, но server-provided чужой legacy root не объявляется проверенным автоматически. Owner создаёт подписанную исходную контрольную точку из доступного локального состояния; она не доказывает полноту исторического состояния, которое уже могло быть скрыто сервером. Shared legacy identities требуют сверки перед выдачей новых ключей. Миграция не удаляет локальные данные, черновики или исторические keys без явного действия.

Legacy kit-only recovery остаётся явно обозначенным прежним режимом до согласованного перехода аккаунта. После перехода он не является fallback: новый generation требует kit v2. Уже скомпрометированный legacy root нельзя отличить от владельца только по тому же legacy kit; такого обещания миграция не делает.

Новые SQLx migration versions уникальны. Старые migration файлы не переписываются. Fixed cache paths `.kamori/local-cache.sqlite3` и `.kamori/mobile-cache.sqlite3` сохраняются.

## Порядок реализации после проверки проекта

1. Воспроизводящие тесты атак; сдерживание desktop bootstrap и всех непроверенных outbound key-release путей; устойчивое состояние заблокированных очередей и честный sync status.
2. Общие account/device certificates и membership manifests, trust bootstrap/invite admission, server DTO/storage, все три семейства клиентов и version gating.
3. Аутентифицированные append/checkpoints/snapshot manifest, durable pins и проверка fork/rollback, миграция legacy spaces.
4. Lost-ACK reconciliation и безопасное переупаковывание допустимых offline writes поверх подтверждённой истории.
5. Отдельный compromise recovery/master rotation, owned/foreign space handoff, crash-safe локальная миграция и сохранение нового kit.
6. Обновление контракта безопасности, hostile-server end-to-end suite, package/native checks и независимое review всей ветки.

Этап 2 добавляет форматы/хранилища и verifiers, но не активирует окончательные key-release гарантии без этапа 3 с аутентифицированным порядком переходов и anchors. Отдельный commit не означает отдельно безопасный production rollout; до полного capability gate допускается только явно ограниченное сдерживание с сохранением локального чтения/черновиков. Legacy неподтверждённая history boundary не переобозначается проверенной.

Каждый этап имеет отдельную implementation task, RED→GREEN, commit и независимое spec/code-quality review. Этап сдерживания не объявляется завершением всего проекта.

## Обязательные отрицательные и положительные проверки

- Подмена device/recovery key, обеих половин device certificate, account UUID/origin/generation, manifest, отозванный сертификат: нет encrypt/upload секретов.
- Подмена desktop inspect key, flow, URI origin, отсутствие/замена commitment, старый bootstrap: master key не выдаётся; обычное и self-hosted подтверждение работают.
- Серверный фальшивый участник и односторонняя подмена root при invite redemption не попадают в последующие rotation recipients.
- Подмена space/epoch/recipient у HPKE package; отозванный автор со старой подлинной подписью и старым подлинным membership manifest не становится допустимой записью в позиции после подтверждённого отзыва.
- Обе стороны append/rotation race; lost ACK до/после ротации; повторный crash; reader downgrade; revoke member/device; недоступная сеть; независимые пространства продолжают работу.
- Отсутствующий middle record, пустой cursor jump, скрытая sibling branch, подмена позиции/предыдущего hash, старый snapshot, неполный stream manifest, fresh-device rollback, fork при сравнении двух клиентов.
- Известный точный replay остаётся идемпотентным; честная перестановка доставки не теряет ветвей; курсор и materialization переживают restart атомарно.
- Reseal после нескольких потерянных ответов согласовывает все attempted digests; compacted payload сохраняет UUID mapping; old-root resume artifact не раскрывает new root; отсутствующий известный исторический key блокирует root commit.
- Старые парольные/reauth/recovery/enrollment proofs отвергаются после смены generation; старый kit не восстанавливает аккаунт после compromise recovery; новый kit восстанавливает.
- Crash в каждой границе local rekey/server commit/ответ; rollback не удаляет единственную доступную копию keys; readonly foreign space требует участия владельца.
- Web и mobile видят одинаковые byte-level test vectors; реальные Rust WASM/FRB пути и packaged native сборки не используют mocks.

## Положительные сценарии и сохранение границ

Эти пункты — будущие критерии приёмки реализации, не результаты уже выполненных тестов.

- **P01:** Web signup создаёт root/profile, корректно подписывает post-signup UUID binding и первое пространство. Native остаётся sign-in-only; mobile Android/iOS не запускает DAV.
- **P02:** Новое собственное web/desktop/mobile устройство получает текущие допустимые ключи под той же account identity. Делегированное device admission и подлинный account trust export работают при offline owner; отсутствие anchor блокирует лишь соответствующее неподтверждённое пространство, не подменяет root и не удаляет локальные данные.
- **P03:** Invite redeem при offline owner даёт чтение переданного snapshot и pending membership; после подписанного admission включается editor. Проверяются 15 и 10080 минут, значения за границами, normalization, expiry, role, повторный/конкурирующий claim и mobile create/redeem; сырой код и pairing secret не появляются в API capture.
- **P04:** Password change сохраняет content root, offline authorization credential, space epochs и читаемость данных; старые sessions/pending proofs отвергаются. Сохранённые passkeys/TOTP работают через новую ceremony; старый challenge через reset не проходит.
- **P05:** Обычный kit-v2 recovery сохраняет root/identity и возвращает текущие ключи; явно подтверждённые сброс факторов и отзыв устройств происходят ровно один раз. Старые drafts остаются blocked-author; kit без seed и words-only fallback отвергаются после миграции.
- **P06:** Единственный owner с единственным утраченным device восстанавливается из полного kit v2: root-authored intent, account commit, crash и delegated finalize без старой session/device signature. Доступны retained server/trusted-export keys/ветви и черновики из сохранившихся доступных кешей; несинхронизированные drafts только на утраченном устройстве kit не восстанавливает. Для успешного space remediation в этом тесте независимо сохранены необходимые trust anchors; конкурирующий recovery, intent revision и cancel до commit не создают неоднозначной authority. После dispatch с неизвестным результатом cancel сначала согласует status, а не объявляет rollback.
- **P07:** Shared/foreign space после root compromise остаётся remediation-pending до независимой сверки нового root владельцем и новой эпохи/manifest. Старый master и все будущие server packages не раскрывают новые эпохи после завершённого и принятого участниками remediation. Изолированная старая ветвь явно остаётся ограничением, а не обещанием немедленного отзыва.
- **P08:** Lost ACK до rotation, reader downgrade и повторный crash согласуют уже принятые attempted bytes без второй логической операции/позиции. Отклонённые author/member drafts сохраняются видимыми; независимое пространство продолжает upload/pull.
- **P09:** Подписанные ownership offer+acceptance передают authority; новый owner ротирует ключи, offline клиент проверяет переход при catch-up. Server-only owner swap и последующий owner-only control прежнего владельца отвергаются.
- **P10:** Для P→Q и offline C(parent=P) causal archive сохраняет ветви Q/C на fresh клиенте. Без проверяемого состояния P запись C удерживается как blocked-causal-history; никакого применения к Q или бесшумной смены parent.
- **P11:** Local browser unlock по умолчанию выключен, сохранение требует opt-in; lock/logout снимает активный доступ без обещания стирания всех копий памяти. Отдельный negative-boundary control показывает, что same-origin script может использовать доступный WebCrypto key: это ожидаемая граница, а не тест защиты от скомпрометированного origin.
- **P12:** Недоступное/ошибочное native secure storage сохраняет recoverable состояние и показывает ошибку, не создаёт plaintext cache/mock fallback. Background resume использует предусмотренную platform policy без нового biometric prompt; account switching не переносит keys/queues/pins между scopes. Физические storage/background свойства проверяются отдельно от simulator.
- **P13:** System projection выключена по умолчанию для каждой коллекции; permission denial не создаёт copies. Выключение с keep/remove затрагивает только проверенные owned copies выбранной коллекции и не обещает удаления чужих backups/cloud copies. Мобильный localhost DAV отсутствует.
- **P14:** Desktop DAV остаётся authenticated loopback-only; неверные credentials и remote bind отвергаются. Положительные проверки CRUD/offline replay/ETag/conflict выполняются с реальным Rust runtime; web/WASM/native/FRB используют общие vectors без production mocks.
- **P15:** В hostile-API bootstrap тесте подменяется весь ciphertext вместе с согласованными attacker root/profile/checkpoints при неизменном подлинном recipient key/flow: native отвергает его до активации данных. Правильный PSK проходит; wrong/empty/short PSK, другой flow/account/scope/checkpoint digest, потерянный fragment, устаревший pending и Base fallback отвергаются. Настоящий trusted-origin desktop и явно настроенный self-hosted portal работают.
- **P16:** При известной компрометации старого master API подсовывает им зашифрованный и подписанный trust export с attacker peer roots/manifest/history. Он не создаёт trusted pins и не получает fresh key packages. Без независимых anchors/сверки история остаётся unverified/salvage и remediation pending; сохранённый настоящий offline anchor и независимая сверка позволяют продолжить проверенный recovery.

## Нормативные ориентиры

- [RFC 9180 §5.1.2](https://www.rfc-editor.org/rfc/rfc9180.html#section-5.1.2): HPKE PSK и аутентификация владения независимо переданным секретом.
- [RFC 9180 §9.7](https://www.rfc-editor.org/rfc/rfc9180.html#section-9.7): application embedding/non-goals и ограничения recipient compromise.
- [RFC 9807](https://www.rfc-editor.org/rfc/rfc9807.html#section-1): OPAQUE и ограничения при компрометации сервера; [§3.3](https://www.rfc-editor.org/rfc/rfc9807.html#section-3.3) различает client-only export key и общий session key.
- [RFC 9420 §3](https://www.rfc-editor.org/rfc/rfc9420.html#section-3): модель групп/эпох; это ориентир, не утверждение MLS-совместимости.

# Authenticated log design for Kamori

Design review only; 2026-10-16; inspected `fix/e2ee-trust-boundaries`. No repository edits, test runs, branches, commits, or real secrets. This is a proposed protocol, not a claim that the current implementation already provides these properties.

## Recommendation and security claim

Ship strict page validation as bounded hardening, followed by a versioned **client-signed append chain** with durable client head anchors, authenticated epoch history, signed complete snapshot manifests, and explicit trusted bootstrap. Add checkpoint exchange over an independently authenticated channel as a required deliverable for cross-device fork detection. Do not describe the first patch, server signatures alone, or single-device history pins as malicious-server consistency protection.

The proposed chain authenticates each included operation's exact position and predecessor and prevents a server from rewriting or skipping a previously anchored history on that client. It does not force delivery, prove that no unseen operation exists, or prevent an isolated server from maintaining separate legitimate concurrent branches for different clients. Once independent views meet, non-extension is detectable; without that contact, indefinite partition and server suppression are indistinguishable. Fail closed on conflicting history while retaining local data and offline editing. Do not silently reset the anchor or pick the longer branch.

Threat assumptions: operation-signing devices, authorized membership administrators, device authorization root, client code, and cryptographic primitives are uncompromised. An authorized malicious writer can author bad application data; an authorized malicious snapshot administrator can lie about state. Stronger protection against those actors requires another policy, such as multiple independent snapshot attestations. A server that can replace the web application's executing JS defeats browser cryptography; protecting executable distribution is separate from this API-server threat model.

## Evidence in this tree

- `packages/crypto-core-lib/src/operation_envelope.rs`: `OperationEnvelopeV1::canonical_signing_bytes` binds IDs, epoch, cipher, nonce, ciphertext, but no server sequence, predecessor, or membership commitment. Preserve its exact existing bytes for compatibility.
- `apps/cloud-server/src/features/operations/dto.rs`: `StoredOperation.space_seq`, append response sequence and `ListOperationsResponse.next_cursor` are outside the envelope signature. `services.rs::list` takes the last returned sequence or `effective_since`; `repositories.rs::list_operations` raises that boundary to server-stored `history_start_seq`.
- `apps/web-frontend/src/lib/components/app/AppWorkspace.svelte::syncSpaceOperations` (around 781–918): raises cursors from `minimumCursor`, applies envelopes, then accepts a larger `next_cursor` before checking whether the page is empty. `flushOutbox` acknowledges and removes drafts from an unsigned append result.
- `packages/crypto-core-lib/src/local_bridge_runner/mod.rs::sync_space` (around 658–832): verifies envelope signatures, but any nonempty page can advance to arbitrary larger `next_cursor`. `register_collection_key_epoch_from` directly raises the cursor from supplied bootstrap metadata. `flush_outbox` acknowledges and removes drafts from an unsigned append result.
- `local_bridge_runner/cloud.rs` decodes these responses; `types.rs` holds runtime transport types; `cache.rs` separately stores materialization, quarantine, outbox and numeric cursors. `store_last_seq` can replace the value; `advance_last_seq` is monotonic numerically but authenticates nothing.
- `pim.rs::PimSnapshotV2` carries `covers_through_space_seq` and all branches of one resource, without a committed full-space stream inventory or authenticated log head. Known-parent/DAG checks and duplicate protection remain useful application checks, but cannot detect omitted independent streams.
- `apps/cloud-server/src/features/spaces/repositories.rs` checks snapshot stream coverage against its own database and inserts rotation snapshots directly into `operation_log`. This must participate in the same new protocol; fixing `/operations` alone leaves a bypass.
- `docs/adr/0003-signed-encrypted-oplog.md` explicitly treats server sequence as transport-only. Revise this ADR to distinguish unauthenticated v1 transport cursors from v2 authenticated positions.

## Stage 1: bounded hardening, with an honest release claim

Extract page validation and application orchestration out of the Svelte component; use shared Rust validation exposed through WASM where practical and identical transport fixtures in TypeScript and native Rust.

Before any page writes, require the expected space, supported kinds/versions, exact safe integer bounds, strictly increasing unique sequence values, no duplicate operation IDs in one page, and an empty page's cursor equal to the requested cursor. For ordinary reads require sequences exactly `cursor + 1 .. cursor + count` and `next_cursor == last.sequence`; derive the committed cursor from validated entries, never a response hint. An empty page leaves the cursor unchanged and means only “no progress returned.”

Contiguity must be checked against actual retention policy. A legitimate history floor or purged prefix cannot be handled by silently accepting a gap. Keep legacy current-state bootstrap as a separately identified **server-trusted legacy boundary** until stage 2; fail closed for unexpected gaps in an established session. Do not call an unsigned `history_start_seq` or `current_state_start_seq` an authenticated boundary. Existing cached cursors may already contain skipped history: this patch cannot repair that by merely pinning the same integer.

Validate every entry's context and signatures before applying any portion of a page. Authenticated application-invalid content can enter durable quarantine and advance verified transport progress only after the corresponding bytes have been retained; invalid signatures, missing authorization proof, chain mismatch or missing key/control transition must not be swallowed as ordinary bad PIM data. Keep transport verification state separate from materialization status so a verified-but-not-materialized state is never labeled fully synchronized.

Atomicity: commit page entries, graph/materialized changes, quarantine and cursor together, or journal verified entries and the head together then perform explicitly tracked replay before claiming materialization complete. A late invalid signature must not leave earlier page mutations accepted as though the whole page passed.

This catches cursor jumps, gaps, duplicate/reordered pages and context substitution that current clients accept. It **does not** catch a server that hides an independent operation and renumbers subsequent v1 envelopes contiguously, nor a fabricated initial directory/history floor, nor a coherent alternate v1 history.

## Stage 2: client-authenticated chain protocol

### Wire objects and canonical bytes

Use explicit `/v2` operations and bootstrap/control endpoints, with MessagePack binary fields (`serde_bytes`/`ByteBuf`). Keep application envelope schema and log protocol version separate. Initially embed unchanged signed `OperationEnvelopeV1` as a payload inside a new log record; do not mutate v1 canonical signing bytes. Add `authenticated_log.rs` in the shared Rust core and export vectors/verification through `wasm_bindings.rs` and `frb_api/crypto_exports.rs`.

Define canonical domain-separated, length-prefixed, fixed-endian bytes; do not sign an arbitrary MessagePack map. UUIDs are 16-byte values, hashes 32-byte values, signatures 64-byte values; lengths checked before conversion. Use SHA-256 and Ed25519 with explicit algorithm/version identifiers. Rust and WASM must use identical canonicalization. V2 wire positions should be fixed eight-byte binary integers or another single specified lossless representation; do not decode arbitrary `u64` into JS numbers. Checked conversion into PostgreSQL/SQLite signed integer range is required.

Proposed minimal signed structures:

```
GenesisV2 = {domain/version, space_id, random_log_id, identity_root_ref,
             initial_membership_head, protocol_policy, migration_manifest_hash?}
AppendBodyV2 = {domain/version, space_id, log_id, index,
                previous_record_hash, payload_kind, payload_digest,
                membership_head_before, key_epoch, committing_device_id,
                append_attempt_id}
SignedAppendV2 = {body, device_signature}
record_hash = H(domain || canonical(body) || device_signature)
payload_digest = H(payload-domain || envelope.canonical_signing_bytes()
                   || length(envelope.signature) || envelope.signature)
ServerReceiptV2 = Sign_server(domain/version, log_id, index, record_hash,
                             previous_record_hash, append_attempt_id)
ObservedHeadV2 = Sign_device(domain/version, space_id, log_id, index,
                            record_hash, membership_head, protocol_floor)
```

Genesis is signed by an owner/administrator key whose identity was independently authenticated through the account/device directory protocol. Index zero commits Genesis; every ordinary/control append starts at predecessor index plus one. `log_id` prevents transplant into a new incarnation of the same space. Pin the server receipt key through Genesis/policy if receipts will be used as transferable evidence; server key rollover must be authenticated. Receipts are evidence of what the server accepted, **not a trust root for the contents or an anti-fork solution**.

A normal append wrapper is signed by the author device and binds its exact envelope digest. If resubmission by another device is later allowed, specify it as a distinct delegation type with separate validation of original author and committing-device permissions; do not introduce implicit reauthorization by wrapping another author's envelope. Control and snapshot commit signers need administrator/snapshot authority defined in authenticated membership policy.

### Write/concurrency and read rules

1. Retain the encrypted offline draft locally. Fetch and verify an extension from the durable local anchor to an observed head, including membership transitions. Only then sign an append proposal for `head.index + 1` and that exact head hash. Persist the proposal before transmission.
2. Server verifies both signatures and membership at the predecessor, then uses a database transaction/CAS on `(log_id, head_index, head_hash, membership_head)` to store the record, payload and updated head together. Receipt derives from that committed record. Exact retry is idempotent and returns the identical record/receipt. Same operation ID with different envelope bytes is a conflict.
3. On an ordinary CAS conflict, obtain and verify the intervening extension, then create a new append attempt against the new head. Preserve the same envelope for unchanged epoch/authorization. If epoch or authorization changed, retain the draft and invoke an explicit authorized re-encryption/re-sign flow; never admit revoked authors just because their draft was created offline. A timeout does not authorize reusing an attempt ID with different bytes: resolve its status first or retry exactly.
4. Validate response against the exact persisted proposal and current pinned predecessor, commit receipt/record/anchor and outbox acknowledgement together. Retain recoverable local ciphertext after upload under local retention policy: a server receipt cannot ensure later storage availability. Do not mark an arbitrary returned sequence as acknowledged.
5. Reads request `(log_id, after_index, after_hash)`, not a bare integer. Every returned header must increment index exactly and link to the preceding record hash. Verify device authorization and signatures before trusting position; payload bytes must match the signed digest. The last verified record derives the next anchor. A response head may advertise additional work but never advances a cursor by itself.
6. A smaller head, different hash at an anchored index, unexpected log incarnation, or response that cannot extend the pin is a trust conflict, not “no updates.” Store evidence and retain the original anchor. Empty reads cannot assert global freshness. A larger valid head that cannot be reached because entries are withheld yields incomplete synchronization, not automatic skipping.

A malicious server can violate CAS and accept concurrent valid proposals on two branches. Client signatures prevent the server from rewriting either branch into the other. This protocol intentionally provides local extension checks and eventual cross-view conflict detection, not global consensus. CAS retries also need fair backoff and bounded work for ordinary concurrency; starvation is availability failure.

### Epoch membership and directory dependency

Do not verify historical operations against only `/spaces/{id}/devices` active rows. Require a retained signed account/device authorization history and a signed space membership state machine: identity roots, key fingerprints, permissions, revocations, epoch recipient commitments and authenticated transition hash. The log wrapper references the exact membership state at its predecessor. Clients compute the membership state while replaying; a server cannot choose an arbitrary older membership proof for a newer position.

A membership transition at index N is authorized under the state before N and activates its new state at N+1. A rotation bundle must bind the old head, previous and next membership hashes, monotonically increasing epoch, exact device/package commitments and complete snapshot manifest; all fields signed by a permitted administrator. Retain old public verification keys and their activation/revocation positions so legitimate historical signatures remain valid after revocation. Reject revoked/read-only devices' appends after their transition boundary. An unseen revocation withheld along an isolated older branch is not detectable until anchor exchange; do not promise real-time revocation to an offline client.

Define the dependency on the directory implementation as an API such as `verify_authorization_at(account_root, directory_head, membership_head, signer, action)`, returning verified historical key and permissions. Pin both directory and log heads in bootstrap bundles. Cross-sign directory references in space membership transitions without requiring circular signatures over their own eventual record hash. Directory publication alone does not change an already signed space epoch: the protocol needs an explicit transition/order rule. The other design workstream must settle enrollment, recovery authority, and root rotations before enabling v2 security claims.

### Snapshots, history floors, and deletion

Add a snapshot manifest binding a precise `(log_id, covered_index, covered_hash, membership_head, epoch)` plus a sorted complete inventory of streams, snapshot-envelope digests, branch/tombstone commitments and explicit quarantined/unmaterialized exclusions. Encrypt sensitive inventory metadata while signing/committing its ciphertext digest. Commit the manifest and all snapshot digests in a signed rotation/checkpoint control payload, authorized by the predecessor membership; perform rotation and publication atomically. Referenced snapshot blobs can be stored separately and need not self-reference the hash of the control record that commits them.

Before applying a checkpoint, verify its chain position/extension to the pin, signer authority, exact inventory cardinality and every referenced blob. An older snapshot cannot replace later locally verified state; a checkpoint is usable only with a verified replay path for subsequent records. A joining device may install an independently authenticated checkpoint anchor and complete matching snapshot bundle as its authorized history floor. Replace scalar `sync_start_seq` APIs with `VerifiedBootstrapAnchor`, an opaque core-produced result, rather than allowing callers to construct trust by passing a number.

Clients that verified the full prefix check the manifest against their own complete inventory and deterministically computed projection, including all conflict branches/tombstones. New devices lacking old decryption keys rely on the trusted administrator's attestation for semantic snapshot correctness and on the inventory commitment for delivery completeness. Per-stream signatures alone cannot prove that the server delivered every stream. Explicit exclusions produce an incomplete/degraded state, not a complete checkpoint.

Retain immutable signed log headers, membership transitions, payload hashes and checkpoint commitments even when policy permits deleting historical ciphertext. A missing expected ciphertext is a sync failure unless an authenticated checkpoint/retention transition explicitly authorizes replacing that prefix with the complete snapshot. Keep transport continuity through historical-header delivery; do not erase positions or renumber after purge. Whole-space deletion may make data unavailable, but existing client pins must not be overwritten by an empty newly created space with the same ID.

The simple initial chain requires O(number of intervening headers) extension verification. For large histories an optional future Merkle accumulator can provide compact consistency/inclusion proofs; it must commit the same client-signed ordered records and anchored roots, not merely add a server-signed cursor. RFC 9162 describes inclusion and consistency proofs and separately notes the split-view limitation of a log acting alone. This design borrows those proof concepts, not a claim of CT compliance. [RFC 9162, sections 2.1 and 11.3](https://www.rfc-editor.org/rfc/rfc9162.html)

## Durable anchors, crash recovery, and new devices

Persist per `(identity/account root, space_id, log_id)` the verified head hash/index, membership/directory heads, minimum protocol version, complete checkpoint reference, and any pending append receipts/conflicts. Never key solely by mutable username or endpoint. Signing/encrypting an anchor authenticates its bytes but does not by itself make an older copy unreplayable.

For ordinary server replay, local SQLite/IndexedDB persistence is enough if intact. To detect restoring an older cache while a separate trusted store survives, native clients also retain the latest head/checkpoint or a digest of an account anchor manifest in platform secure storage. OS keychain storage is not a universal monotonic counter and can also be restored/erased; do not claim immunity to rollback of all device storage. Browser IndexedDB provides no independent antirollback root: clearing it requires trusted bootstrap, never silent TOFU disguised as continuity. A recovery file's pinned head protects only through its export time.

Use a crash-safe two-phase local anchor update: transactionally store verified entries plus a pending anchor journal; persist the secure-store high-water anchor; finalize the database's published head/materialization acknowledgement. Resume unfinished journals on startup. A secure-store head ahead of the cache requires reconstructing and validating the path from a saved lower checkpoint to that exact hash, then replay; it must not be lowered to match the cache. A DB pending head ahead of secure storage must be reverified before publishing/pinning. For web, entries/state/anchor share an IndexedDB transaction and multi-tab coordination uses a per-space lock plus compare-and-swap on the old hash.

Bootstrap choices:

- Existing trusted device: authenticated pairing transfers account root, directory/membership heads, per-space log anchors and protocol floor in a signed bundle bound to the new device key and a fresh challenge. New device verifies transfer identity using the directory/pairing design and proves all server data extends those pins.
- Recovery artifact: recovery-authorized bootstrap includes at least the most recent exported pins and protocol floor. The server can withhold everything since that export; display that recovery freshness limit. Recovery keys alone prove decryptability/authority, not the latest log position.
- No surviving anchor or authenticated peer/witness: create an explicitly unverified initial-view trust decision according to product policy, or refuse secure recovery. Never claim rollback detection from account login or an otherwise valid old snapshot. Do not silently merge that state into a previously anchored identity.

Log out, credential rotation and access-token refresh must preserve trust anchors. Explicit local-data deletion may remove them but requires future trusted bootstrap. Copying the database to a new device must not copy signing identity as an unnoticed continuation.

## Stage 3: independently delivered checkpoint exchange

Exchange `ObservedHeadV2` bundles through authenticated peer pairing/direct channels, user-exported comparison codes/files, or an independently operated witness whose key and policy are pinned. Ordinary writes may also carry recent observed heads for useful gossip, but gossip delivered only by the same malicious server can be suppressed forever.

For equal index and different hashes, retain both signed heads (and server receipts when available) as direct inconsistency evidence. For different indices, request the header extension from the earlier head; a different hash at that earlier position proves divergence. Withholding the proof is an inability to verify/availability failure, not mathematical proof of equivocation. Devices must never sign an observed head unless they verified its extension from their own pin.

An optional strict mode can require an independent witness acknowledgement before treating remote state as confirmed. Witnesses enforce append-only extension and retained per-log state. State the exact trust/quorum model; independent witnesses that all collude provide no benefit. This sacrifices online availability when witnesses cannot be reached; offline editing stays local and pending. Checkpoint timestamps/nonces can establish recent contact with a witness, but even that does not prove every unsubmitted or suppressed operation was included.

## Migration and rollout

Introduce schema/endpoints and dual-capable clients before activating a space. Existing v1 operation bytes remain immutable/readable; the server cannot manufacture a trustworthy historical chain by backfilling sequence values and signing them itself.

A trusted owner device reconciles its local data and available v1 history, produces a signed migration checkpoint containing a complete current-state manifest, legacy per-operation digest inventory (or its commitment), the chosen v1 boundary, and new Genesis/policy. Independently available devices compare their known operation digests and snapshots before approving migration; a disagreement blocks automatic activation. This provides a truthful baseline for the inspected history only: already omitted v1 operations unknown to every participating client cannot be retrospectively proven absent.

Activation CAS binds the chosen legacy boundary and exact signed migration artifacts, quiesces v1 writes, and atomically enables v2. All later writes, membership changes, rotations, invite joins and snapshot publications must use v2. An old client receives an explicit upgrade-required error; never wrap its newly uploaded v1 content in a server-signed substitute. V1 envelope format may remain the inner encrypted payload format, but new uploads need client-signed append wrappers. Offline legacy drafts are retained and admitted only after upgrade verifies membership and signs the v2 wrapper (or reencrypts for a new epoch).

Clients pin the minimum protocol version with the new Genesis and transfer it in recovery/pairing. A removed capability response, missing proof, v1 endpoint fallback, different Genesis or stale recovery bundle cannot lower that floor. Clients with no prior pin remain subject to the bootstrap limitation, so a directory-level authenticated required-protocol policy is also needed. Rollback of deployment means v2 spaces become read-only/unavailable until repaired, not automatic downgrade. Schema is additive initially; no removal of v1 history until independently validated checkpoint/retention policy permits it.

## Exact negative tests and acceptance criteria

Use deterministic keys and local fake malicious transports; no real secrets or broad suites for this design review. Add tests alongside implementation and run targeted checks before broader required gates.

- Web/native: `empty_page_cannot_advance_cursor`; `nonempty_page_next_cursor_above_last_rejected`; `page_gap_rejected_before_materialization`; `reversed_duplicate_or_fractional_sequence_rejected`; `wrong_space_valid_signature_rejected`; `late_invalid_signature_leaves_page_state_unchanged`.
- Demonstrate stage-1 limitation deliberately: hide one independent v1 stream, renumber remaining envelopes contiguously, show v1 validation cannot distinguish this. V2 counterpart must reject changed position/predecessor/digest without the original device's signature.
- Core: `rejects_relabelled_signed_append`; `rejects_payload_or_signature_digest_swap`; `rejects_wrong_log_incarnation`; `rejects_previous_hash_mismatch`; `rejects_unknown_critical_version_or_algorithm`; `canonical_bytes_match_wasm_native_vectors`; `rejects_wire_integer_overflow`.
- Writes: `receipt_must_match_persisted_proposal`; `duplicate_returns_identical_record_receipt`; `conflicting_duplicate_preserves_original`; `cas_race_loser_rebases_only_after_verified_extension`; `lost_response_retries_exact_attempt`; `fake_accepted_reply_does_not_delete_outbox`; `crash_during_ack_retains_payload_or_committed_receipt`.
- Epochs: `revoked_key_valid_before_transition_invalid_after`; `read_only_member_cannot_commit`; `server_supplied_old_membership_cannot_authorize_new_position`; `rotation_chain_links_to_old_head`; `unknown_control_blocks_advancement`; `rotation_append_race_has_single_atomic_order`; `omitted_package_or_recipient_commitment_rejected`.
- Snapshots: `valid_old_snapshot_cannot_replace_newer_pin`; `snapshot_wrong_covered_hash_rejected`; `missing_extra_or_duplicate_manifest_stream_rejected`; `omitted_tombstone_or_conflict_branch_rejected_against_verified_projection`; `quarantined_exclusion_never_reports_complete`; `unsigned_history_floor_cannot_bootstrap`; `purged_payload_requires_authenticated_replacement`; `retained_headers_preserve_chain_after_compaction`.
- Durability: crash at every journal/secure-store/DB finalization boundary; restart must produce old verified state or recoverable newer state, never a falsely advanced materialized cursor. Test secure-store-newer-than-restored-DB recovery, browser cache clearing requiring bootstrap, account/space scoping, concurrent tabs/background writers, reauthentication preserving anchors, and sign-out not resetting protocol floor.
- Recovery: `stale_server_snapshot_rejected_against_pairing_anchor`; `pairing_bundle_bound_to_new_device_and_nonce`; `recovery_artifact_only_guarantees_exported_floor`; `replayed_v1_capability_cannot_downgrade_pinned_space`; `old_client_v2_append_rejected`; `migration_disagreement_blocks_activation`; `legacy_unknown_omission_not_falsely_claimed_detected`.
- Fork harness: server feeds A and B two valid concurrent client-signed branches; each progresses while isolated (document expected limitation). Independent exchange then detects incompatible heads; neither resets or merges the pin. Different-height withholding yields verification unavailable, not false equivocation proof. Genuine extension at different heights succeeds. Server-only gossip suppression does not falsely report global agreement. Witness-strict mode stops confirmation when the witness is unreachable while retaining offline edits.

# Independent adversarial validation: E2EE trust-boundary design

Reviewed: `docs/superpowers/specs/2026-10-16-e2ee-trust-boundaries-design.md`, commit `7d2f0d5255c8620a0fcfdf2de2eb758e1bb1c8c4`, 2026-10-16. Read-only review of the proposed architecture, not implementation verification. Repository AGENTS.md was read. Supporting identity/lifecycle reports were consulted as explanatory material; prior approval was not inherited. No repository files or secrets were changed/read, and no product test suite was run.

**Verdict: revision required. One high-severity architectural trust gap, plus one medium-severity unresolved revocation contract.** The explicit limitations on freshness, historical secrecy and compromised client code are generally sound. The untrusted-API threat is not fully closed by the stated desktop bootstrap.

## H1 — Bootstrap authenticates the recipient but does not authenticate the root delivered to the recipient

**Severity: High. Actual architectural defect.**

**Locations:** `docs/superpowers/specs/2026-10-16-e2ee-trust-boundaries-design.md:54`, `:56`, `:58`, with circular own-root check at `:42` and fresh-client anchor import at `:82`.

**Counterexample:**

1. Honest native client generates its HPKE pair and opens the correctly configured browser origin with the correct key commitment and flow UUID. Honest browser verifies exactly these values; no recipient substitution occurs.
2. The malicious API withholds the honest browser's encrypted bootstrap response. The native public key, flow and public AAD are known to it.
3. The API chooses a master root it knows and constructs a fresh HPKE ciphertext addressed to the genuine native key, carrying that root, a matching attacker-signed profile and forged initial checkpoints. It retains the same public flow/context fields.
4. Native successfully decrypts. Comparing the supplied identity with the root derived from the delivered master, as line 42 requires, succeeds. Everything after this can be internally signed and consistent under the attacker's root. The client has no previously pinned root on this first enrollment.
5. An otherwise honest native client can now create or import plaintext into a workspace whose recovery authority is known to the attacker. The server did not need to learn the original account master. It replaced the first trust anchor.

**Why existing text does not close it:** The trusted native-to-browser launch channel establishes the browser's expected recipient, not the native client's expected browser/account sender. Public AAD and a public recipient commitment do not establish sender identity. A self-consistent delivered master/profile/signature is not an independent anchor. Adding an HPKE Auth sender key inside the same unauthenticated response has the same circularity. The explanatory identity report at line 86 checks the master against the included profile and only says native *can* display/confirm identity; it does not require an authenticated reverse binding either. The broad label “trusted bootstrap” is not a construction for the missing direction.

**Minimal architectural correction:** Require native to authenticate the browser-approved root, generation, account/service identity and checkpoint export independently of the API before installing the master or enabling data use. Select a concrete trust mechanism: for example, a fresh high-entropy bootstrap secret carried only through the trusted local launch channel and used to authenticate the complete return transcript with an existing MAC/HPKE-PSK construction; or a mandatory independently transferred/compared browser-to-native root/transcript confirmation. The secret must not be sent to the API or logged there. Bind the transcript to native recipient key, unique flow and one-use lifecycle as well as approved root and anchors. A signature is sufficient only if its verification key is already independently anchored. Add a hostile-API test that replaces the whole bootstrap ciphertext and matching root/profile/checkpoints while preserving the honest recipient key and flow; native must reject before accepting any account state or exposing new plaintext.

**Primary-source basis:** RFC 9180 distinguishes encryption-to-public-key from authenticated modes and identifies sender authentication as an additional property of PSK/Auth/AuthPSK. Neither public context nor self-supplied identity is an independent sender anchor. [RFC 9180 §5.1](https://www.rfc-editor.org/rfc/rfc9180.html#section-5.1), [§9.1](https://www.rfc-editor.org/rfc/rfc9180.html#section-9.1). The attack is a protocol-level inference from those properties and this spec, not a claim about a tested implementation.

## M1 — Ordinary device revocation lacks a stated confidentiality contract and mandatory escalation for master-bearing devices

**Severity: Medium. Actual specification coverage gap; not a failure of the fully invoked compromise-recovery protocol.**

**Locations:** `docs/superpowers/specs/2026-10-16-e2ee-trust-boundaries-design.md:18`, `:88`, `:90`, `:96`; negative revoked-certificate acceptance criterion at `:133`.

**Counterexample:** A lost or compromised native device retains its provisioned master (the desktop handoff explicitly gives it one). The user selects the separately named device-revocation action at line 88. Its certificate/session is revoked, but the document never states that this action enters the root and space remediation workflow. A later space rotation still wraps the fresh space key to the unchanged account recovery identity. The attacker derives that private recovery key from the retained master and a hostile server supplies the fresh package. Even rotating only the space epoch would not fix that. An account-root signing key derived from the retained master also remains available to mint new certificate/account-state signatures, subject to whatever admission policy is eventually implemented.

**Why existing text is insufficient:** Line 18 names lack of epoch rotation on device revoke as a confirmed cause; line 88 lists device revocation independently but specifies no transition for it. Lines 90–98 describe explicit master-compromise recovery and its limitations; they do not tell the user or implementer when device revocation must invoke it. Rejecting the old certificate is useful authorization enforcement, but does not revoke the master or a recovery HPKE private key. The supporting lifecycle report does contain the missing rule at line 65 (runtime devices possess master; suspected compromise defaults to root compromise), but line 165 makes the target specification authoritative.

**Minimal correction:** Define ordinary device/session revocation as an authorization-only operation with no confidentiality guarantee against a device retaining master material. Require the “lost/compromised master-bearing device” path to enter the full root replacement and affected owned/foreign space remediation flow; state that disabling one certificate or merely changing an epoch cannot restore secrecy while its retained recovery root remains a recipient. Add a test in which a revoked-device adversary retains the old master and obtains all future server packages: after completed remediation it cannot decrypt new epochs or regain admission using old-root signatures. Keep the existing honest-server API denial claim separate from malicious-server cryptographic guarantees.

## Claims that survive adversarial validation at this abstraction level

- **Malicious recipient substitution:** Independently pinned member roots, root-signed device certificates, owner-authorized recipient manifests and recipient/generation/manifest-bound packages are a sound direction. Server directory rows never become authority merely by being fetched. Root/recipient checking must precede encryption/upload, as line 96 correctly requires.
- **Invitation admission:** A separate invite signing key derived from a high-entropy out-of-band capability and a claim signed by that key plus the new root can prevent a server holding only lookup material from substituting a new member. This proves capability possession, not human/legal identity. Code interception or a malicious recipient is outside this narrower claim. Exact signed grant/claim fields, expiry checked by clients, conflict handling and trust provenance remain implementation-plan obligations; the supporting identity report provides a useful transcript sketch. They should not be silently omitted during planning.
- **Authorization history:** Applying transitions according to the preceding authenticated state (line 44), using historical certificate authorization (line 78), and pinning chain heads prevents replay of an old authentic manifest *after the client has accepted the revocation on that branch*. This does not prove global recency, and the document correctly does not promise it.
- **Offline writes:** The document expressly limits absence to a verified head, reconciles every attempted envelope for one logical UUID, binds replacement to a CAS head, and preserves blocked drafts. It also requires client-side UUID uniqueness after compaction. Those address the stated duplicate/lost-ACK ambiguity at architectural level; a concrete proof structure and crash/concurrency schedule still need implementation work.
- **Log attacks:** Chained, authorized commitments and anchored checkpoints justify detection of altered/missing interior records and observed rollback. Concurrent honest writers can still be partitioned into individually valid extensions by a malicious service; cross-device checkpoint comparison detects divergence when performed. There is no quantitative freshness bound or guaranteed time to detect a hidden tail. Lines 26, 82 and 84 acknowledge this, so “bounded freshness” must mean an explicitly shown verified boundary, not a wall-clock freshness guarantee.
- **Compromised root signing:** An attacker with the old root can forge signatures under that root, including plausible identity transitions. Line 98 correctly requires independent verification of replacement identity rather than treating old-root signatures as recovery proof. The separate recovery-authorization seed helps only where an honest verifier enforces it; it is not a magic defense against the specified malicious server. Lines 94 and 96 acknowledge this distinction and delayed revocation on isolated branches. The missing device-revocation policy is M1, not a refutation of these caveats.
- **Origin/system plaintext:** A hostile executing web origin or unlocked endpoint can use keys/plaintext; opt-in system projection creates external plaintext copies. Lines 22, 28 and 100–106 state appropriate boundaries and do not promise zeroization, retroactive secrecy or deleting third-party backups.

## Important implementation-plan obligations rather than invented architectural blockers

1. Specify normal password change, normal kit recovery, password enrollment, kit-only replacement enrollment and compromise recovery as distinct state machines. Define which combinations of password, independent factor, full kit and surviving device allow each operation. Never represent total loss of all decryption capabilities as recoverable by server authentication. The target currently goes deepest on compromise recovery; routine flows need positive acceptance cases.
2. Bind an OPAQUE-wrapper's authenticated contents to account/service and generation and verify the root against any durable local pin. OPAQUE can supply a client-only export key, whereas its session key is known to the server; these must not be confused. OPAQUE does not provide newest-version evidence for arbitrary application wrappers. A new device lacking an independent checkpoint cannot infer newest membership state from a successful password login. [RFC 9807 §3.2–3.3](https://www.rfc-editor.org/rfc/rfc9807.html#section-3.2).
3. Specify the authority for every account/device state transition, including own enrollment under a master-derived root, admission of that device to each space, revocation tombstones, root-generation changes and per-space owner approval. Preserve availability expectations for a valid own-account password enrollment when a foreign space owner is offline without silently admitting unverified recipients.
4. Define canonical transcripts, domains, package commitments, signed invitation expiry/role/context, snapshot state coverage, complete inclusion/non-inclusion evidence and all-space/account lock participation. These are necessary deliverables, but detailed encodings need not already exist in an architectural document that explicitly defers them at line 165.
5. Fresh kit-only recovery can authenticate the kit's account root and generation but the listed kit fields do not contain per-space history anchors. A destroyed-device recovery therefore has the explicit no-anchor freshness limitation at line 82. Do not claim the negative “fresh-device rollback” test at line 138 proves detection below a checkpoint that was never independently retained.

This review supplies counterexamples and requirement validation only. It does not supply source-level evidence that any proposed guarantee is implemented.

## Scoped assessment of proposed H1 correction (not a reread of revised target)

The coordinating reviewer proposed a native-generated independent random 32-byte pairing secret, delivered only through the trusted local URL fragment/QR and never to API/query/logs; required standard HPKE PSK mode with nonempty transcript-bound `psk_id`; authenticated context covering version, origins, unique flow/nonces, native recipient, browser-approved account root/generation and exported anchors; existing local pin checks before activation; no Base-mode fallback; local expiry/cancellation/cleanup. **This construction closes H1 at architectural level under the stated trusted-client-code assumption**, since the hostile API can no longer construct an accepted replacement using only the public native key. Outer server/session routing must remain a consistency check: authenticated browser-approved identity is authoritative and cannot be replaced by server metadata. This assessment applies to the proposed correction; the numbered findings above describe the committed target actually reviewed.

## Scoped rereview of revised normative draft

Reviewed `/private/tmp/kamori-e2ee-vv-20261016/spec-revised.md` (revision 2), including VV-S1, VV-S2, VV-T1, the new own-device/export delegation at line 48 and P01–P15. Also read the supplied six-pass standalone `hpke 0.14` probe log; those are primitive demonstrations, not product verification.

- **H1 closed in revised text:** lines 66–72 mandate a 32-byte native-generated out-of-band secret, standard HPKE PSK mode with application guards, authenticated return payload, pending-context and existing-pin checks, and one-use expiry. Lines 64/68 preserve recipient authentication and prevent untrusted outer fields from becoming identity authority. P15 directly covers whole-ciphertext/root substitution.
- **M1 closed in revised text:** line 106 expressly limits administrative revoke and requires root/space remediation for suspected compromise of master-bearing devices. P07 supplies the intended retained-old-master adversary acceptance criterion.
- **Ownership transfer is adequate at architectural level:** line 52 requires predecessor-owner authorization, new-owner acceptance of the same offer, independently verified successor root, authenticated ordering and CAS. Compromise of an authorized owner remains a compromise of that authority until remediation; signatures cannot solve it alone.
- **Own-device delegation is reasonable for an uncompromised root:** line 48 restricts delegated authority to the member's own devices/unchanged roles and orders admission through prior state. Server-replayed exports still lack recency, as correctly stated. A root being authorized by the current state is essential, not merely any mathematically valid certificate.

### R1 — Compromised-root exports must not authenticate fresh peer pins during compromise recovery

**Severity: High if the new export permission applies during compromise recovery; unresolved normative ambiguity requiring a short explicit exception.** Locations in revised draft: `/private/tmp/kamori-e2ee-vv-20261016/spec-revised.md:48`, `:114`, `:126`, `:187`.

Line 48 newly accepts an account-signed/encrypted export under the account master as an authentic source of peer pins. This is justified for an uncompromised master. It is not justified when that master is the explicitly modeled stolen old root. An attacker holding M_old can create a matching encrypted/signed export with attacker-controlled peer pins and forge the old owner's signed manifests. A user recovering after losing every device can import this internally consistent export, generate M_new, and rotate an owned shared space to the attacker peer roots now labeled verified. The new epoch is then exposed despite rekeying the owner. Other participants verifying the new owner's root, as line 116 requires, does not authenticate the recovering owner's copied peer pins to that owner. A forged export can also assert a misleading history anchor; it must not be described as authentic evidence merely because it verifies under a compromised key.

**Minimal correction:** In compromise recovery, explicitly disallow establishing peer pins/history authority from exports whose only authentication depends on the compromised old master/root. Preserve independently retained trusted anchors where available; otherwise independently reverify foreign member identities before releasing fresh keys, and retain unanchored recovered history as unverified/salvage rather than claiming established integrity. Ordinary password enrollment under an uncompromised root can keep using the authenticated export with its stated freshness limitation. Add a recovery test supplying a forged old-master-authenticated peer-pin export; fresh epochs must not be encrypted to its substituted roots. No new cryptographic primitive is required.

**Scoped verdict at this read:** original H1/M1 are closed; R1 needs the explicit compromised-root exception before approving this newly added export rule. No product implementation claim follows from the standalone probes or this review.

## Final scoped R1 closure

Reread only the final R1-related changes in `/private/tmp/kamori-e2ee-vv-20261016/spec-revised.md`: VV-R1 at line 50, offline-kit anchors at line 114, conditioned lost-device recovery P06 at line 188, and adversarial acceptance criterion P16 at line 199. **R1 is closed at architectural-specification level.** The explicit exception prevents old-master-only exports, checkpoints and manifests from establishing peer/recipient/history authority after known compromise; it requires independent retained anchors and confirmed recipients or independent reverification before fresh key release, rejects automatic authority changes signed by the old compromised owner/root, and keeps unverifiable recovery in pending/repair with salvage history. Offline kit anchors establish only their retained observation boundary, not subsequent freshness. P06 no longer promises unavailable device-only drafts or unconditional full remediation without independent anchors. P16 targets the identified forged-export attack directly.

**Final scoped verdict: no unresolved blockers from this security-model review. H1, M1 and R1 are closed in the revised normative draft.** This is closure of the reported architectural findings, not blanket approval of unreviewed future changes, a wire-protocol proof, or verification of product implementation. No additional product edits or tests were performed in this final check; earlier review history above is preserved.

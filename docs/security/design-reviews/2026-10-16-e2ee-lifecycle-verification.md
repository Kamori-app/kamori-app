## L1 — P1: Payload compaction preserves receipt identity, but not enough state to preserve offline semantic parents

**Spec locations:** lines 66, 78–80; acceptance requirements lines 137, 139–140.

Line 66 requires resealing the same semantic operation with the same dependencies. Line 78 guarantees retention of signed commitments and UUID→envelope-digest/position mappings after payload purge. Line 80 guarantees a snapshot of all current streams/branches. These three properties do not guarantee that an old dependency remains materializable.

**Counterexample:** P is a committed edit. Online device A commits Q(parent=P). Offline device B has an unaccepted edit C(parent=P), potentially a field-level change. A rotates the epoch and publishes a complete snapshot whose single current branch head is Q. P's encrypted payload/base state is purged under the signed checkpoint. B returns, proves C absent through H, and reseals C with its original dependency P. The log and UUID inventory verify correctly, but a newly recovered client with snapshot Q cannot derive the old materialized state of P to apply C or reconstruct the P→Q/P→C conflict. Applying C on Q silently changes semantics; rejecting it prevents the promised permitted offline write from being materialized. Knowing P's digest/position proves occurrence, not its content or semantic DAG.

**Source feasibility evidence:** `packages/crypto-core-lib/src/pim.rs:37–49` defines field-level mutations with semantic dependency UUIDs; `:546–563` snapshots contain branch head UUID and materialized projection, not ancestor states; `:618–625` requires every parent in the graph. `packages/crypto-core-lib/src/local_bridge_runner/mod.rs:933–947` requires the actual dependency state and uses it as the materialization base. This is a substantive data-representation requirement, not a wire-encoding detail.

**Minimal correction:** Specify what authenticated causal/base-state evidence survives compaction for any still-supported historical parent. Either retain/retrieve an authenticated archive sufficient to reconstruct those parent states and DAG edges, or define verified dependency capsules supplied by returning writers. If the product instead imposes a supported offline/history horizon, explicitly retain such writes as blocked drafts and require reviewed import after that horizon; do not claim unchanged automatic reseal there. Add a test with P→Q compacted to Q, an offline C(parent=P), and a fresh client applying the resulting branch without changing C's parent.

## L2 — P1: Root replacement has no defined authorization handoff into the existing authenticated space log

**Spec locations:** line 44, lines 76–78, lines 92–98.

Line 44 requires every account/device/membership transition to be authorized by the state immediately before its log position. Lines 92–94 first replace account identity and revoke every old device/session; line 96 then remediates owned spaces using the new identity/manifest. A replacement-device bootstrap restores API access, but the text does not specify how that new root/device becomes an authorized author of the first transition in an existing space whose predecessor still names the old root/devices.

**Counterexample:** A personal space has one owner root R0 and one allowed device D0. The owner commits compromise recovery to R1/D1, revoking D0 and placing the space in remediation-pending. The pinned log head H still authorizes R0/D0. A transition signed only by R1/D1 is unauthorized under H. A transition submitted as D0 hits the revocation rule; using R0's signature alone as an exception conflicts with the stated compromise boundary for other participants (line 98). Simply treating the current server account profile as authorization bypasses line 44. The text needs to choose an explicit exception/handoff; independently verifying R1 is necessary but does not itself define the log transition's admissibility or which bytes that approval covers.

**Source feasibility evidence:** `apps/cloud-server/src/features/auth/repositories/account_recovery_attempts.rs:170–180` currently revokes all active devices and deletes device packages; the rotation path at `apps/cloud-server/src/features/spaces/repositories.rs:675–705` currently relies on server membership/owner identity. Neither existing endpoint supplies the missing client-verifiable recovery transition authority. This is not asserting that an implementable handoff is impossible: a preauthorized exact transition, or an explicitly pinned recovery-handoff rule, can solve it.

**Minimal correction:** Normatively define one recovery handoff transition, its predecessor/head binding and signer authority, the independent verification prerequisite for shared-space clients, and the narrowly scoped permission to submit it after old-device revocation. Distinguish its control append from prohibited ordinary writes during remediation. Alternatively, atomically preauthorize exact owned-space handoffs as part of the account commit with a stated conflict/retry rule. Add single-owner/single-device and shared-owner tests starting at H, crashing after account commit, and resuming the first authorized new-epoch transition without resurrecting D0 or trusting an arbitrary server identity.

## L3 — P1: Identity-generation replacement does not specify the authentication-generation transition needed to invalidate old password proofs

**Spec locations:** line 92 and required test line 141.

Line 92's atomic mutation lists the OPAQUE wrapper, recovery verifier, identity generation, package set, old sessions/devices, and unfinished recovery/enrollment capabilities. It does not require advancing the independent authentication generation or invalidating unfinished password/reauthentication flows. Line 141 explicitly requires old password/reauth/recovery/enrollment proofs to fail after the generation change. Identity generation and authentication generation are not interchangeable in the current implementation.

**Counterexample:** A password signin starts at auth generation A and produces a valid OPAQUE proof. Root rotation commits identity generation I+1, retaining ordinary configured credentials and revoking existing sessions as specified. The unfinished signin is not a session and is neither recovery nor enrollment. If auth generation remains A, completing that old proof after commit creates a new valid session. Session revocation alone does not invalidate the in-flight proof; analogous continuation paths must be audited. A literal implementation of line 92 therefore fails line 141.

**Source feasibility evidence:** `apps/cloud-server/src/features/auth/services/signin.rs:103–115` compares `proof.auth_generation` to `user.auth_generation`; `apps/cloud-server/src/features/auth/repositories/authentication.rs:8–22` binds deferred mutations to that separate generation. The existing account reset explicitly increments it at `apps/cloud-server/src/features/auth/repositories/account_recovery_attempts.rs:144`; ordinary password changes do so in `repositories/refresh_tokens.rs:487`. Merely adding identity generation to the new endpoint will not inherit this safeguard.

**Minimal correction:** Include `auth_generation` increment in the same account-rotation transaction, explicitly separate it from identity/recovery/inventory generations, and require every old authentication and enrollment continuation to retain/check the generation captured at authorization, in its final mutation transaction. If preserving configured passkeys, define whether pre-commit passkey assertions/challenges must also be invalidated; current discoverable passkey completion reads the current generation at finish (`services/passkeys.rs:216–250`), so merely incrementing a counter does not bind such a challenge to its earlier issuance. Keep the narrow exact-retry/status exception. Add interleaving tests that begin each relevant flow before commit and finish it afterward.

## Additional implementation-plan clarifications (not independently blocking the architecture)

1. **Inventory updates, not only inserts/deletes — line 96.** Extend the normative inventory-generation rule to in-place changes affecting coverage, entitlement, recipient identity, or authenticated package bytes. Existing recovery/device package publication is an upsert (`spaces/repositories.rs:181–183`, `:426–427`), and member revocation/epoch changes are updates (`:875`, `:962`). The previous review's final paragraph already requires equivalent in-place mutations, but the authoritative line 96 still says only insertion/deletion. Specify deterministic ordering for multiple accounts/devices as well as spaces where a rotation touches several recipients. Do not invoke the existing advisory account-security helper before discovering/acquiring required space locks without reviewing the full lock graph.

2. **Capability staging — lines 122–125.** Account/device manifests are delivered before the authenticated log on which their activation semantics depend. State that step 2 is additive and its final-strength key-release paths cannot activate until step 3's authenticated activation/anchors are available, unless a separately labeled containment protocol is specified. Separate commits need not be separately deployable, so this is a delivery clarification rather than an inherent cycle.

3. **Bounded preparation, cancellation, and crash liveness — lines 92–96.** The architecture correctly keeps old recovery usable before commit and forbids rollback of secure-store pins. Implementation tasks should define chunked staging/coverage limits without silent truncation, cancellation before/after commit dispatch, exact-retry/status retention, and native write ordering (durable journal before anchor advancement; verified local catch-up after it). A repeated inventory-CAS failure or permanently missing known key must remain a visible blocked/repair state, never “recovery completed.” Define how unrelated spaces remain usable during retry. These details can live in tasks if their safe outcomes are made explicit.

## Assessment of proposed RecoveryIntent correction

A pre-commit, old-root-authorized typed `RecoveryIntent` in each owned-space log can close L2: it binds the exact recovery operation/manifest, old head, replacement root/device, freezes ordinary writes, and explicitly delegates only the matching new-root finalize. Account commit verifies complete intent/inventory coverage; afterward the replacement bootstrap submits the delegated control without reviving old-device ordinary-write authority. Peers independently verify the replacement root; old-root signature alone does not suffice. Pre-commit cancellation appends an abort; post-commit recovery resumes without reverting to old root.

Three details must accompany that correction: (a) lost-all-device kit-only recovery needs narrowly scoped root-authored intent submission without an unavailable old device signature/session; (b) control finalization/abort must be explicit exceptions to the ordinary-write freeze; (c) inventory-CAS restart changes an exact manifest digest, so intent revision or append-only abort/reprepare must be defined. Concurrent root-recovery intents need generation/operation CAS so only the committed recovery's delegation remains eligible. These are small additions to that chosen handoff, not a request for all wire fields now.

This supplies an implementable path from a single old owner to the new device without granting that device arbitrary authority under the old membership.
- **L3 closed — lines 118–122, P04–P05 at lines 184–185.** Authentication, identity, recovery authorization, and inventory generations are explicitly distinct; auth generation advances atomically and late known-account mutations recheck the captured generation. Discoverable challenges use an issuance barrier ordered with security commits, avoiding a wall-clock race or reading only the current generation at finish. Retained credentials may start a new ceremony; they cannot carry a stale ceremony across the boundary.

Accounts and devices, as well as spaces, have deterministic ordering; account-first helpers cannot precede required space locks. - **Cancellation/crash clarification addressed at architecture level — lines 116, 124, P06/P12.** Unknown commit results require reconciliation, not a declared rollback; native secure-storage failure must preserve recoverable state without insecure fallback. Chunked staging limits, capability retention, and journal-before-anchor ordering remain detailed implementation-plan items from the earlier report. They were not architectural blockers and no implementation evidence is claimed for them.

One nonblocking acceptance-contract correction remains: **P06 line 186** describes all devices lost and then says all known historical keys/branches/drafts are available. A kit cannot recover unuploaded drafts whose only copy is on an unavailable lost device. Qualify the assertion to retained server/trusted-export content and accessible local caches; state that unavailable unsynced device-only content is outside kit recovery. This does not undermine the RecoveryIntent handoff.

## Actionable findings

1. **High: existing ownership transfer has no authenticated successor-owner rule.** D:44 makes the owner-signed membership manifest authoritative and requires transitions to be authorized by the state immediately before their log position. This is a sound foundation, but the document never identifies ownership transfer as a transition or defines which owner may authorize the first successor manifest. Existing product behavior explicitly supports offer/acceptance (`SPEC.md:124-126`). Current code changes the security-space owner and old/new owner roles (`apps/cloud-server/src/features/ownership/repositories.rs:444-460`); the web UI exposes offer and acceptance (`apps/web-frontend/src/lib/components/app/SettingsModal.svelte:1112-1170`). If implementation follows only the current API result, a malicious server can name a successor; if it pins the original signer forever, legitimate transfer stops working. Add a normative ownership transition, authorized by the verified predecessor owner and binding the independently authenticated successor identity, space/generation, offer/acceptance and predecessor head; define activation/replay/conflict handling. Add positive transfer → next owner rotation → offline-client catch-up and negative server-only owner substitution/old-owner post-transfer control tests. Workspace ownership and security-space ownership need an explicit distinction because only the latter controls the cryptographic recipient manifest.

2. **Medium: positive acceptance scenarios are promised but mostly not made reviewable.** D:10 names registration, device enrollment, invitation, revoke, recovery and lost-response retry. D:133-143 concentrates on attack and race cases; only ordinary/self-hosted desktop bootstrap (134), replay/reordering/restart (139), and new-kit recovery (141) explicitly state successful outcomes. Add concrete happy paths with final state and participating clients: web signup and initial profile/UUID routing binding; password sign-in and provisioning of a new own web, desktop and mobile device; invite redemption while owner is offline followed by owner admission and editor enablement; normal password change with unchanged root and continued content access; normal kit recovery with its intended factor/session/device behavior; owned-space compromise recovery and foreign-owner handoff, including retained historical access. State which API/UI actions are web-only and which native families must verify/use the resulting protocol. Byte vectors alone (143) do not demonstrate these lifecycle outcomes.

3. **Medium: question 5 has requirements but no explicit acceptance cases.** D:102-106 correctly bounds browser-origin compromise, native storage and plaintext projection; D:149 correctly requires real native builds and does not substitute simulator evidence for physical-device guarantees. D:133-143 never exercises browser local-unlock consent/lock/logout, unavailable native secure storage, background resume with real storage access policy, default-disabled per-collection projection, permission denial, disable-and-keep versus disable-and-remove owned copies, or authenticated loopback DAV. Add regression acceptance for these preserved security boundaries and explicitly retain the limitation that same-origin code can use unlocked keys and external backups cannot be erased. Current storage/projection paths are listed under question 5 below.

4. **Medium: explicitly retain invitation TTL and sign-in-only native constraints in the proposal's compatibility criteria.** D:48 preserves generated one-time invite codes and strengthens their entropy; D:112 and 118 explicitly preserve MessagePack bytes and fixed caches. Web-only registration, native sign-in-only, and user-selected 15-minute through 7-day expiry appear in current `AGENTS.md:12-14`, `SPEC.md:29-30,108-115`, and implementation, but are not repeated in this proposal or its acceptance requirements. There is no contradiction today; make these preservation requirements explicit before the new signup/routing and invite-admission paths are implemented. Cover TTL boundaries and both server normalization/validation and mobile create/redeem paths as required by `AGENTS.md:75`.

5. **Clarification: normal kit recovery after v2 migration needs a distinct acceptance contract.** D:88 distinguishes normal kit recovery from compromise recovery; D:90-96 specifies root replacement in considerable detail; D:116 rejects legacy fallback after migration. It remains unclear from the acceptance list whether normal full-kit-v2 recovery retains the same account identity/root, which independent credential/proof it consumes, and what it does to TOTP/passkeys/devices and old-author drafts. Existing recovery deliberately disables TOTP and revokes sessions/passkeys/devices without replacing the master root. Do not infer that the new compromise-recovery semantics automatically specify the ordinary recovery path. Define this distinction and a positive regression test before implementation; otherwise tests can pass by exercising only root replacement.

## Traceability to the five questions

1. **Can a compromised server replace a new device public key and obtain space keys?**

Current assertion supported. `apps/web-frontend/src/lib/components/app/SettingsModal.svelte:950-970` loads existing space keys and encrypts them to `entry.device.hpke_public_key` with no client-authenticated ownership check in that flow. Rotation fetches server `/members` and `/devices` (`AppWorkspace.svelte:1752-1766`) and encrypts the new key to the returned device keys and member recovery bundle (`1782-1807`, bundle parsing `1632-1648`). Mobile does the analogous fetch/encrypt (`packages/crypto-core-lib/src/frb_api/invites.rs:169-231`). Its shape/version/length validation does not authenticate a foreign account root.

Desktop starts with a locally generated ephemeral key but opens the API-returned `verification_uri` without a trusted-origin comparison (`apps/dav-bridge-desktop/src-tauri/src/commands/auth.rs:719-745`). The approving browser directly takes the inspect-returned HPKE key, encrypts the account master key and uploads it (`AppWorkspace.svelte:267-297`). This supports D:14-15. The function comment at desktop `auth.rs:713` calls the origin trusted, but executable code at 744 does not enforce that assertion.

The proposal's controls are D:40-50 (account-root/device certificate, independent first trust, authenticated membership, package binding, invitation claim/grant, one checking API) and D:54-58 (native-supplied trusted link and recipient commitment before encrypt/upload). Required attack cases appear in D:133-136. Own-account identity is derived from the locally unlocked master root (42); other-account roots need the independent invite/bootstrap channel. This distinction avoids inventing manual verification for every routine own-device enrollment. Missing happy paths and ownership succession are findings 1-2.

2. **What happens to a removed member's offline operations and to epoch/sync races?**

Current assertion supported twice. `apps/cloud-server/src/features/operations/services.rs:55-67` checks current role/epoch before entering the append repository. The repository again checks current epoch (`repositories.rs:86-96`) and active membership/device authorization (`109-139`) before looking for an exact duplicate (`142-149`). Thus an already accepted operation with a lost response cannot be acknowledged through ordinary append after rotation/revocation. This ordering is deliberate current authorization policy, not evidence that revocation should be bypassed.

Web replays exact queued envelopes and stops the global loop on the first error (`AppWorkspace.svelte:917-955`). Native replays queued envelopes for the selected space and propagates its first append error (`packages/crypto-core-lib/src/local_bridge_runner/mod.rs:1833-1849`). The native implementation is per-space here, so the phrase "queues stop on first error" in D:16 is accurate; it should not be expanded into a claim that both implementations necessarily stop all spaces globally.

D:62-70 defines durable queue states, per-space independence, read-only receipt lookup, proof of inclusion or head-bound absence, reconciliation of every attempted digest, CAS reseal only for a still-authorized original author, and locally retained blocked drafts for removed/revoked/reader authors. D:76-78 preserves logical UUID uniqueness and proof after compaction. D:137,139-140 supplies meaningful races/replay/restart coverage. A concrete positive test must assert one logical change after lost ACK and exact retry, preserve pending drafts for a removed author, and continue an independent space; broad test labels alone should not count as evidence.

3. **What happens to OPAQUE/master/key packages during password change, recovery and device loss?**

Current assertions supported. Normal password change wraps the active, unchanged master key using the new OPAQUE export key (`apps/web-frontend/src/lib/components/app/SettingsModal.svelte:516-538`). Server updates the OPAQUE record/wrapper and increments auth generation/revokes refresh sessions (`apps/cloud-server/src/features/auth/repositories/refresh_tokens.rs:478-505`); it does not rotate the account root or space epochs.

Recovery reconstructs the same root from the 24 words and wraps it under the new OPAQUE export key (`apps/web-frontend/src/lib/components/app/AccountRecovery.svelte:94-127`), decrypts returned recovery packages (`135-142`), resets web device credentials and locks the vault (`144-149`). Server binds reset to exact request bytes (`apps/cloud-server/src/features/auth/services/password.rs:155-180`), updates OPAQUE/wrapper and auth generation while clearing TOTP (`repositories/account_recovery_attempts.rs:143-151`), revokes refresh sessions/passkeys/devices and device packages and clears backup codes (`156-185`), and retains only the completed exact request for idempotency (`117-130,187-202`). It returns current recovery key packages (`services/password.rs:183-191`). The stored account recovery verifier/public identity and space epochs are not replaced by this reset. A stolen original root can derive the same kit verifier; normal recovery is not root-compromise remediation.

Device revoke revokes the device and its sessions and deletes its packages, without rotating any space epoch (`apps/cloud-server/src/features/devices/repositories.rs:88-131`). This supports D:18 and agrees with `SPEC.md:77-95`; avoid saying normal recovery preserves old sessions/devices, since source explicitly revokes them.

D:88-98 distinguishes all four actions and proposes independent kit-v2 authorization, action-scoped proof, retained current/history key coverage, transactional account commit, independently protected resume state, surviving exact-retry/replacement-device capability and subsequent owned/foreign-space remediation. D:141-142 covers old/new credential and crash rejection cases. Finding 5 identifies the remaining ordinary-recovery acceptance ambiguity. Lost-device scope must distinguish unavailable/lost hardware from an attacker holding its still-readable root: device revoke alone cannot erase cached secrets or rotate their descendants.

4. **Can omission/reordering/replay of signed operations produce incorrect client state?**

Current assertion supported. `packages/crypto-core-lib/src/operation_envelope.rs:87-100,114-137` authenticates the envelope identifiers/epoch/type/nonce/ciphertext, not server `space_seq` or page `next_cursor` (`apps/cloud-server/src/features/operations/dto.rs:14-29`). Web adopts page.next_cursor and saves state before its empty-page break (`AppWorkspace.svelte:902-912`); native adopts page.next_cursor after processing a nonempty page (`packages/crypto-core-lib/src/local_bridge_runner/mod.rs:821-829`). The native empty-page branch does not adopt an empty jump, so a finding claiming that exact path for both families would be inaccurate. Neither current envelope signature binds a complete sequence or snapshot inventory.

D:74 gives bounded initial transport hardening; D:44 and 76-84 define a predecessor-authorized control/history chain, CAS append, retained UUID/digest mapping, authenticated complete snapshot manifest, durable atomic pins and independent checkpoint comparison. D:26 and 84 explicitly exclude guaranteed fresh-tail/fork detection without an independent channel. D:136,138-140 covers stale genuine authorization, gaps, replays, lost branches, old snapshots, new-device rollback and restart. These are architectural requirements, not properties proved by current tests or by the existing signed-envelope format.

5. **What happens to keys/data under compromised browser origin, lost hardware and OS projection?**

D:22,28 and 102-106 state appropriate limits: executing client-origin malware/unlocked endpoint compromise can read client-accessible material; JS zeroization is limited; non-exportable WebCrypto does not defeat same-origin code; native storage protects files subject to platform policies; external system copies/backups remain outside Kamori's erasure guarantee. These agree with current `docs/whitepapers/security-and-privacy.md:47-55,91-105,119-126` and `SPEC.md:237-249`.

Concrete storage evidence: desktop master/cache keys are in system keychain (`apps/dav-bridge-desktop/src-tauri/src/commands/common.rs:247-274,325-349`); mobile secure device vault and local cache key use `KeychainAccessibility.first_unlock_this_device` (`apps/dav-bridge-mobile/lib/src/services/sync_runtime_storage.dart:82-90,256-290`). That accessibility policy supports background operation after first unlock; it is not a per-operation biometric/user-presence promise. Web `cryptoVault.ts:895-900` clears active key references on lock, which does not prove erasure of every JavaScript/runtime copy.

Mobile projection is explicitly opt-in plaintext (`apps/dav-bridge-mobile/lib/src/services/system_projection_service.dart:46-50`), requests permission and persists enabled choice before projection (`90-132`), and offers owned-copy removal separately from disabling (`135-180`). D:106 preserves this boundary without claiming backup deletion. Physical-device review should verify key accessibility/backup settings rather than merely restating package names. Finding 3 supplies missing acceptance coverage.

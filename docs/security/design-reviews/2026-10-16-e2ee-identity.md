# Authenticated account, device, recovery, membership, and desktop bootstrap design

Status: architectural review only, 2026-10-16; branch `fix/e2ee-trust-boundaries`. No product files edited, no commits, no heavy suites. ## Recommendation and scope

Use a master-derived Ed25519 account identity root, account-signed recovery/device certificates, owner-signed space membership state, code-derived invitation join proofs, and locally pinned version/hash checkpoints. Authenticate desktop bootstrap recipients through a desktop-constructed browser fragment containing the locally generated recipient commitment. Treat server responses as delivery candidates, never authorities for identity or membership.

This closes server-selected recipient keys without making existing password login require an already-online device. A new client that successfully unlocks the existing master key independently reconstructs its own identity root, certifies its locally generated device keys, and registers them. An invite holder authenticates the owner's identity through the independently conveyed invitation secret and proves its own root to the owner using a code-bound join claim. Registration stays web-only; desktop/mobile remain sign-in-only.

Threat boundary: trusted installed clients and trusted browser application code; malicious API/storage service and substituted, omitted, replayed, or reordered responses. A server that can ship arbitrary browser JavaScript can read an unlocked web vault; this proposal cannot promise protection against that distinct threat without independently authenticated client delivery. Do not call TLS, JWTs, server enrollment tokens, database constraints, or a self-signed server-delivered bundle an independent identity anchor.

## Alternatives considered

1. **TOFU pins plus server-delivered self-signed certificates.** Small change; detects later root swaps after first use. Does not stop a malicious server substituting the very first recovery key/device root or adding a new fake member. Safe only if explicitly labeled TOFU and excluded from automatic high-value key redistribution. Not adequate as the fix.
2. **Master-derived identity root + authenticated invitation grants + signed membership/checkpoints (recommended).** Reuses current master/recovery/login machinery and shared Rust; works across web/WASM, mobile/FRB and desktop. Costs protocol v3 metadata, authenticated membership history and a migration handshake for legacy shared members. Local rollback detection is strong after observation, but global freshness and equivocation prevention need another channel/witness.
3. **Device trust graph/MLS with external key transparency witnesses.** Can offer stronger group-state consistency, device revocation semantics and independently witnessed freshness. Requires a much broader protocol and operations migration, offline/group-recovery policy and actual independent witnesses. A log operated solely by the same untrusted server does not eliminate split views. Appropriate future project, not a minimally invasive repair to this architecture.

## Shared signed protocol and anchoring

Add `packages/crypto-core-lib/src/identity_trust.rs` (name proposed) containing all signing, strict parsing, canonical transcript, trust resolution and package binding. WASM/FRB expose protocol operations; JavaScript and Dart must not reimplement signature transcripts.

Use Ed25519 signing seed `HKDF-SHA256(master, info="kamori.account-identity-signing-seed.v1\0")` and the existing independent recovery-key derivation. Use strict Ed25519 verification and reject weak keys; validate HPKE key usability as current code does. Account fingerprint is SHA-256 over a domain-separated canonical service scope and root public key. Scope is a precisely specified canonical origin/base-path identity, not a server-returned string. Fix URL normalization once in Rust and use shared vectors, including case-sensitive path semantics.

MessagePack transports byte arrays (`serde_bytes`/`ByteBuf`), but **do not sign arbitrary map serialization**. Sign fixed binary transcripts with versioned domain prefix, fixed-width numeric fields, fixed UUID/key lengths, and length-prefixed strings/bytes. Define enum tags explicitly; reject unknown versions/duplicate fields, bad lengths and inconsistent duplicated fields. Every signature and hash has a separate domain; deterministic fixture vectors must match native/WASM/FRB.

Proposed objects:

- `AccountProfileV3`: protocol version, service scope, root public key/fingerprint, recovery public key, identity generation, profile revision, previous profile hash, optional username claim; root signature. Username is a display claim until independently bound, not the cryptographic identifier. Initial signup can sign without server UUID; after signup publish a root-signed routing binding to assigned `user_id`. Clients pin that binding and reject silent changes. The server UUID remains a routing identifier, not the trust root.
- `DeviceCertificateV1`: root fingerprint, service scope, server-user binding digest, device UUID, signing public key, HPKE public key, platform/usage, certificate serial, issuance/account-state generation, root signature. Add device signing-key proof of possession over the same transcript (prevents accidental misbinding; root authorization is the decisive trust check).
- `AccountStateV1`: root fingerprint, monotonically increasing revision, previous state hash, sorted active certificate digests, explicit revoked device IDs/serials, profile hash, root signature. An unsigned `active=true` must never override a signed revocation. Avoid wall-clock-only revocation logic.
- `SpaceMembershipStateV1`: space ID, pinned owner root, monotonically increasing revision, previous hash, key epoch, sorted member root fingerprints + routing bindings + roles + history floors, accepted invitation/claim digests, removals, signer authorization. Owner signature or explicit previously certified owner delegation. Sign ownership transfer by previous and next owners; server ownership metadata cannot establish a new authority.
- `SpaceKeyPackageV2`: context includes service, space ID, key epoch, membership head hash, recipient root fingerprint, exact recipient certificate/profile digest and recipient usage (`device`/`recovery`). Bind context in HPKE info/AAD and sign package/context by an authorized issuing device/owner. HPKE alone does not establish who authorized a recipient or application freshness. See [RFC 9180, sections 8–9](https://www.rfc-editor.org/rfc/rfc9180.html#section-8).

Own-account trust: derive root and recovery key locally after OPAQUE unwrap, recovery-kit import, or independently bound desktop bootstrap; require exact match to any published own profile. Never derive the expected root from `public_key_bundle`. Existing local device private/public key pairs must be internally checked before signing their certificate. Signing a server-provided list of devices wholesale would simply certify the attack.

Other-account trust: root is established by an authenticated invitation/acceptance exchange or explicit independently compared fingerprint. Persist provenance as `own-master`, `invite-secret`, `manual-fingerprint`, `legacy-tofu`, or `unverified`. Only the first three authorize redistribution. "Verified via invite" means possession of the invite capability conveyed through that external channel, not a claim about someone's legal identity. Replacing an existing fingerprint requires a valid old-root/new-root transition and/or fresh independent verification; no auto-repin on signin or successful server authentication.

## New devices, status, rotation, and offline behavior

Password new-device sign-in unlocks master; local root signs locally generated device certificate. Publish profile/certificate/account-state transition through authenticated APIs with compare-and-swap on previous state hash. An existing own device verifies the certificate under its independently derived root before sending any space key. A newly enrolled device recovers current permitted space keys with its locally derived recovery private key and creates its own device package as today. This avoids an unnecessary dependency on owner being online for each ordinary device enrollment.

Before rotation/approval, resolve the complete recipient set from a verified space-membership head plus per-account signed active-device state. Fetch responses are candidates checked against that state: reject unknown added member, root mismatch, foreign user/device binding, certificate mismatch, missing expected member/state, revoked target, duplicate/conflicting IDs, unsupported version, and checkpoint rollback. Server omission should produce an availability/error condition, not silently sign a shrunken membership roster or change intended revocation targets. Never bootstrap trust merely because a candidate knows the old shared space key: every former/shared member may know it.

Persist new checkpoint and planned rotation/outbox transactionally before releasing/uploading key packages. Save revision+hash and all relevant authorization evidence with operation state. Concurrent tabs/devices use existing lifetime locks plus CAS; on conflict fetch/verify chain and recompute from intended action. Never merge server rows into an unsigned local trust list. Historical author certificates remain archived, while key issuance uses current signed status.

Revocation limitation: all current clients receive the account master key. A compromised client that retains it can derive both account-signing and recovery keys and fabricate new valid device certificates. Signing device revocation does not remove that capability. Defending against master-compromised devices requires rotating master/root/recovery keys, rewrapping account material and space keys, and independently reconfirming affected memberships; alternatively redesign client master access and use a separate offline root. This proposal addresses malicious-server key substitution, not post-compromise security with a shared retained master.

## Invitation protocol preserving code-based sharing

Keep user-created invite codes and 15-minute–7-day TTL. Never send raw code to the server. Add a versioned format; old bare-key invitations cannot securely establish identities.

1. Owner rotates/snapshots current state using only verified existing recipients. Generate code locally; derive distinct encryption key and Ed25519 invitation signing seed from code with separate domains. Publish the public invitation verification key in an **owner-signed invitation grant**: service, client-generated invite UUID, lookup hash, space ID, owner root, membership head, prepared epoch/rotation, role, history floor, expiry, and invitation verification key. The server can verify redemption signatures without knowing the code.
2. Encrypt an invitation payload under the code-derived AEAD key with grant digest/context AAD. Payload includes space key, owner profile, signed grant, signed space-state checkpoint and all identity context needed to compare the server's outer response. Owner stores grant and pending invite in encrypted account trust storage. An invite shared through an authenticated outside channel anchors its embedded owner root; the lookup hash alone does not.
3. Recipient retrieves candidate payload, decrypts and verifies all context against the grant and user-entered code. Build a join claim binding exact grant digest, service/space/epoch/role, recipient root profile and routing binding, local device certificate, random claim ID. Sign claim with both derived invitation signing key and recipient root. Upload claim; never merely post the lookup hash as cryptographic authorization. Owner or other clients can verify code possession against the owner-authorized invitation verifier, without holding raw code.
4. Owner automatically validates claim at next sync and records a signed membership transition consuming that invite exactly once. Only this signed state authorizes wrapping future epochs to the newly joined root. Recipient can decrypt the invited current snapshot immediately (as existing code semantics permit); show membership/write authorization pending until signed acceptance arrives. If immediate editor writes while owner is offline are mandatory, allow explicitly delegated provisional authorization with known fork limits and careful one-use rules; do not silently pretend server single-use rows are cryptographic finality.
5. Receipt and root pin survive restart and new-device encrypted trust-state transfer. Once accepted, later own-device certificates under the pinned root do not need a fresh invitation. All future recovery wraps require the root-authenticated profile; all future device wraps require certificate + signed status + membership.

Code possession grants capability, not unique personhood. Anyone to whom the code leaks may produce a valid claim. Two valid claims for one invite require explicit conflict handling; a malicious server can partition clients and suppress conflicts. Owner acceptance creates one authoritative observed chain, but global single-use/freshness cannot be proven to indefinitely isolated clients without independent witnesses. TTL must be signed and checked on clients; malicious service clock/expiry metadata cannot be its sole enforcement.

## Desktop bootstrap: independently bind the master-key recipient

Current `verification_uri` and ten-character `user_code` both originate at server, so displaying/matching only that code does not prevent recipient substitution. Existing HPKE flow-ID binding proves ciphertext belongs to the chosen key/flow, not that browser chose the legitimate desktop key.

- Native generates fresh ephemeral HPKE pair and a 32-byte client nonce before `/start`. Maintain local pending record with recipient public/private key, nonce, canonical portal/service origin, server flow ID, code, protocol version and expiration. Flow ID and code may still be server routing values.
- Native constructs `/app?...` URL itself from an explicitly trusted configured portal origin (may differ from API origin; persist user/app configuration, never trust start-response arbitrary origin). Append fragment containing version, locally generated recipient public key or full SHA-256 commitment, nonce, flow ID and code. Include origin in commitment transcript. Never put master key/private key/poll secret in URL. If keeping server URI as a hint, validate exact origin/path and rebuild query/fragment from local expected fields; reject credentials, unsafe schemes and unexpected redirects/origin changes.
- Browser captures fragment into session-local pending state before login/navigation; clears fragment from location/history once retained. A complete desktop-originated commitment is mandatory. It may fetch `/inspect` but must compare returned flow and public key against fragment transcript and reject mismatch before invoking encryption. If carrying full public key, use that key directly after validation. No fallback to an uncommitted `/inspect` key.
- V2 bootstrap HPKE context binds service/portal origin, flow ID, nonce, recipient key/commitment, protocol version and approved account fingerprint/routing identity. Payload includes master, approved account profile and encrypted trust-checkpoint export; native checks the recovered master-derived root against the included account identity and local transcript. Native can display/confirm authenticated browser account identity; do not trust outer server-returned username as the payload identity.
- Approval remains a user gesture, with local-derived fingerprint/SAS displayed in desktop and browser if supporting manual cross-device entry. The existing server code remains a lookup identifier. For manual code-only entry, require scanning/copying the full local commitment or a sufficiently strong out-of-band fingerprint confirmation; do not claim a short attacker-grindable server-controlled SAS gives full binding. A public-key-only self-signature/PoP delivered by server does not authenticate recipient identity.
- Missing/changed fragment, lost pending state, unsupported bootstrap version, mismatched account/origin/flow/nonce/key or duplicate consumed flow fails closed. New native client retries start; old clients must update. Key zeroization and cleanup should follow current failed-session cleanup paths.

Independent anchor here is the OS-mediated locally constructed URL or separately compared desktop fingerprint, assuming trusted browser code. Hashing a server-provided key and displaying it only in browser would not fix this.

## Rollback and first contact: exact claims

Local pinned root detects root swaps, signed status detects unauthorized key changes, and persisted revision+hash detects older observed heads and same-revision forks. Require verifiable previous-hash continuity for advances; unknown legitimate root transitions need explicit old-root authorization or re-verification. Keep tombstones after revocation to prevent device-ID reuse.

A brand-new device with only master key can reconstruct **own identity**, but cannot know the latest peer pins, account roster revision or space revocation state from the malicious server alone. Import an authenticated checkpoint from an existing device (desktop bootstrap can carry it), locally retained/recovery-exported checkpoint, or independent witness; otherwise label peer/member state "freshness not independently confirmed" and require re-verification before redistributing secrets. A master-encrypted backup on the same server gives authenticity but not newest-version assurance. Offline existing devices can use pinned keys/local data; they must not approve new recipients from unverifiable remote state.

No local-only protocol can provide absolute first-contact human identity authentication or prove that no newer state exists when all information arrives through the same hostile server. TOFU must be explicitly distinguished from invitation/fingerprint verification. A malicious server can always withhold data/updates; these fixes must fail closed without claiming availability or universal fork prevention.

## Migration and compatibility

1. Add shared types/verifiers and additive server BYTEA storage: account profiles/bindings/state heads/history; device certificate and signed status; space membership heads/history; invitation grants/claims/receipts; context-bound key package version. Use new unique numeric SQL migration prefix. Extend all duplicated DTOs and regenerate committed FRB/WASM surfaces.
2. Existing users unlock master to derive own root and publish a signed v3 profile. Verify published old recovery public key matches local derivation, but old server record never becomes the anchor. Self-certify only locally held device keys with possession checks; every other device upgrades on next genuine unlock. Do not mass-certify existing server device rows.
3. Existing shared members lack verified external anchors. Keep readable cached data where valid, but block key redistribution/rotation to those members until a new invitation-based verification exchange or independently compared root fingerprint establishes them. Re-verification can preserve existing membership/history floors; a refresh handshake need not silently reset permissions. Show a precise "member identity needs verification" error. Server cannot mark migration complete for a client.
4. Legacy unsigned keys, v2 bundles, legacy invites and code-only desktop approvals are not acceptable recipients in new writes. Reject downgrade rather than trusting optional/default-empty certificates. Native clients must upgrade to participate in new enrollment/sharing/approval; old generated artifacts and mocks must not bypass policy. Recovery-kit master reconstructs root; restoring latest peer checkpoints still has the freshness caveat above.
5. An honest server should reject new insecure mutations once protocol migration is enabled, but client policy is authoritative against a malicious server. Root-protected local minimum protocol version prevents rollback by an HTTP feature flag. Preserve registration-only-on-web, bytes-oriented MessagePack and existing native cache paths/platform scope.

## Required negative and compatibility tests

- Fake server returns attacker HPKE key with same legitimate device ID, altered signing key, wrong user/account root, or swapped recovery key; web rotation, web Settings approval, FRB mobile rotation and native provisioning reject **before any key package upload**. Test with an attacker private key to show it cannot recover any emitted secret.
- Entire attacker root/profile/device chain is internally well-signed but not pinned/authorized by membership: reject. Added member with valid self-signed certificate: reject. Unauthenticated owner/role/history-floor replacement: reject.
- Own master-derived root/profile mismatch and local public/private mismatch fail; valid password signup/login, kit recovery, local-only device enrollment and later recovery package unwrap work on all surfaces.
- Certificate changes any signed field, incorrect lengths/weak keys, wrong domain/version, malformed/duplicate MessagePack fields, ambiguous transcript, cross-origin/cross-account reuse: reject with shared fixture vectors.
- Old account/space state, same-revision different hash, skipped unverifiable chain, revoked certificate replay, stale signed roster excluding revocation, unknown target, missing expected member, duplicate IDs: fail closed at the documented checkpoint boundary. Include fresh-device test proving the implementation does not mislabel unproven freshness as verified.
- Invite lookup hash alone cannot create valid join claim; changed recipient root, device, space, role, epoch, expiry, owner root, routing binding or grant fails. ## Delivery boundary

The minimum complete repair includes recipient certificates **and** an independent account/member anchor **and** all active outbound key paths. Shipping only signed public bundles or fixing browser rotation alone leaves exploitable paths. Desktop recipient commitment is independently implementable but needs browser/native coordinated protocol gating. Global key transparency and master-compromised-device recovery are separate explicit future designs, not properties to imply from this patch.

## Small first implementation phase for approval

Phase 1A is a coordinated native/browser bootstrap V2 change: local portal URL construction and fragment commitment, mandatory browser expected-recipient validation, transcript-bound HPKE context, protocol-version rejection of old approvals, pending-state/cleanup changes, and malicious-API negative tests. It has no dependency on cross-account membership redesign and directly removes the account-master-key recipient substitution.

Phase 1B introduces shared master-derived own-account root/profile/device certificate primitives and verified-own-recipient resolution in WASM/FRB/native. Publish v3 own profiles/certificates through additive server DTO/storage changes; gate web Settings device approval against the locally derived root and current signed device-state evidence. Preserve ordinary own-local password enrollment and recovery unwrap; do not certify arbitrary server rows during migration. Route all own-account wraps through this policy and add swap/legacy-negative tests.

Until later phases implement authenticated invite grants/claims and membership state, fail closed on redistribution to unauthenticated other-account recipients. Do not sell Phase 1 as complete shared-space trust repair; existing shared members need explicit verified migration, and automatic shared-space rotation may be blocked until that happens. Phase 2 completes invite/acceptance/member-state migration and all cross-account rotation paths, followed by history/operation-author verification and durable checkpoint integration. Author verification and checkpoint work required by a security claim must land before making that claim; phase boundaries are review boundaries, not permission to retain an insecure fallback.
